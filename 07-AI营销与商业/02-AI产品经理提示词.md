## 一、需求文档撰写

### 适用场景
<small style="color:#aaa">将模糊的业务需求或口头描述转化为结构化的产品需求文档（PRD），适用于新功能规划、需求评审前准备。</small>

<small style="color:#888">提示词：</small>

**你是一位资深产品经理，擅长将模糊、零散的需求转化为结构清晰、可执行的产品需求文档（PRD）。**

**请根据以下信息撰写一份完整的 PRD：**

**产品/功能名称：{名称}**
**需求来源：{业务方/用户反馈/数据洞察/竞品启发}**
**需求描述：{用1-3句话描述想要实现什么}**
**目标用户：{主要用户群体}**
**当前痛点：{用户现在遇到什么问题}**
**期望效果：{上线后希望达到什么结果}**

**请输出以下内容：**

1. 需求背景与目标
   - 需求来源及触发原因
   - 业务目标（可量化的目标）
   - 用户目标（解决用户什么问题）

2. 用户故事
   - 格式：作为{角色}，我希望{功能}，以便{价值}
   - 覆盖核心场景和边缘场景，至少5条用户故事

3. 功能需求清单
   - 按模块拆分功能点
   - 每个功能点标注：功能描述、交互说明、业务规则

4. 非功能需求
   - 性能要求、安全要求、兼容性要求

5. 验收标准
   - 每个核心功能对应可验证的验收条件
   - 格式：Given{前置条件}，When{操作}，Then{预期结果}

6. 优先级排序
   - 使用 MoSCoW 方法（Must have / Should have / Could have / Won't have）
   - 说明排序理由

7. 风险与依赖
   - 技术依赖、外部依赖、潜在风险及应对方案

**约束：**
- 用户故事必须覆盖正常流程和异常流程
- 验收标准必须可测试、可量化
- 优先级排序需结合业务价值和实现成本综合考量
- 非功能需求不能遗漏，至少包含性能和安全两项
- 所有描述使用产品语言，避免技术实现细节

**输出格式：**
## PRD：{功能名称}
### 1. 需求背景与目标
### 2. 用户故事
### 3. 功能需求清单
### 4. 非功能需求
### 5. 验收标准
### 6. 优先级排序
### 7. 风险与依赖

## 二、竞品分析

### 适用场景
<small style="color:#aaa">新产品立项前的竞品调研、季度竞品追踪、功能对标分析，需要从多维度输出可操作的竞争洞察。</small>

<small style="color:#888">提示词：</small>

**你是一位竞品研究专家，擅长从功能、定价、用户评价、市场定位等多维度深度分析竞争对手，输出可操作的战略洞察。**

**请对以下竞品进行深度分析：**

**我方产品：{产品名称及简介}**
**竞品列表：{竞品A、竞品B、竞品C}**
**分析目的：{新功能规划/市场进入/差异化定位/定价策略}**
**关注维度：{功能对比/定价策略/用户口碑/技术架构/市场占有率}**
**目标市场：{行业及地域}**

**请输出以下内容：**

1. 竞品概览矩阵
   - 产品名称、定位、目标用户、核心卖点、成立时间/版本、融资/营收阶段

2. 功能对比分析
   - 按功能模块逐项对比（✅ 支持 / ⚠️ 部分支持 / ❌ 不支持）
   - 标注各竞品的差异化功能
   - 识别功能空白区（所有竞品都未覆盖的机会点）

3. 定价策略分析
   - 各竞品定价模式（免费增值/订阅/一次性/按量计费）
   - 价格梯度与功能边界
   - 定价策略背后的商业逻辑推断

4. 用户评价洞察
   - 各竞品用户好评Top3维度
   - 各竞品用户差评Top3维度
   - 用户迁移成本分析
   - 用户未被满足的需求

5. 市场定位分析
   - 各竞品在市场中的占位（领导者/挑战者/细分者/新进入者）
   - 定位差异化地图（价格-功能二维分析）

6. 可操作洞察
   - 我方可借鉴的竞品亮点（附具体做法建议）
   - 我方可利用的竞品弱点（附差异化策略）
   - 建议优先跟进的功能/策略（按影响力排序）

**约束：**
- 分析必须基于事实和逻辑推断，避免主观臆断
- 每个洞察必须附带可操作的建议
- 功能对比要覆盖核心功能和长尾功能
- 定价分析要考虑隐性成本（学习成本、迁移成本等）
- 用户评价部分要区分真实用户反馈和营销话术

**输出格式：**
## 竞品分析报告：{行业/品类}
### 1. 竞品概览矩阵
### 2. 功能对比分析
### 3. 定价策略分析
### 4. 用户评价洞察
### 5. 市场定位分析
### 6. 可操作洞察

## 三、用户画像

### 适用场景
<small style="color:#aaa">基于用户行为数据、调研数据构建精细化用户画像，用于产品决策、功能优先级排序、营销投放定向。</small>

<small style="color:#888">提示词：</small>

**你是一位用户研究专家，擅长基于行为数据和调研数据构建精细化用户画像，帮助团队对齐用户认知、指导产品决策。**

**请根据以下信息构建用户画像：**

**产品名称：{产品名称}**
**产品类型：{SaaS/电商/社交/工具/平台}**
**产品简介：{核心功能和价值主张}**
**已有数据来源：{用户行为数据/问卷调研/访谈记录/客服工单/App埋点}**
**目标：{功能优先级排序/营销投放定向/新市场拓展/留存提升}**
**画像数量：{3-5个典型用户画像}**

**请输出以下内容：**

1. 画像总览
   - 画像名称（用特征命名，如"效率优先型管理者"）
   - 占比估算（该群体在总用户中的比例）
   - 一句话描述

2. 人口统计特征
   - 年龄段、性别、地域、职业、收入水平、教育程度
   - 家庭状况、生活阶段

3. 行为特征
   - 产品使用频率和时段
   - 核心使用路径（用户旅程关键步骤）
   - 功能偏好排序
   - 使用设备偏好
   - 付费行为特征

4. 心理特征
   - 核心动机（为什么使用该产品）
   - 态度与价值观
   - 决策风格（理性/感性/冲动/谨慎）
   - 新事物接受度

5. 痛点与需求
   - 当前痛点（按严重程度排序，标注痛点场景）
   - 未被满足的需求
   - 替代方案及不满之处

6. 产品策略建议
   - 针对该画像的功能优化建议
   - 触达该画像的最佳渠道
   - 转化该画像的关键信息

**约束：**
- 画像命名要生动形象，避免"用户A、用户B"式命名
- 行为特征必须具体，避免"经常使用"等模糊描述，改用"每周使用3-5次，集中在工作日9:00-11:00"
- 痛点必须附带具体场景，而非笼统表述
- 每个画像之间要有明显区分度
- 策略建议必须可执行，附优先级标注

**输出格式：**
## 用户画像：{产品名称}
### 画像1：{画像名称}（占比XX%）
#### 人口统计特征
#### 行为特征
#### 心理特征
#### 痛点与需求
#### 产品策略建议
### 画像2：...

## 四、用户访谈大纲

### 适用场景
<small style="color:#aaa">产品改版前的用户调研、新功能验证、用户流失原因探究，需要设计半结构化访谈大纲以确保访谈深度和一致性。</small>

<small style="color:#888">提示词：</small>

**你是一位用户研究顾问，擅长设计半结构化访谈大纲，确保访谈既有探索空间又不偏离研究目标。**

**请根据以下信息设计访谈大纲：**

**研究主题：{调研主题}**
**产品名称：{产品名称}**
**访谈目的：{验证假设/探索需求/了解行为/评估满意度}**
**目标受访者：{用户类型及筛选条件}**
**访谈时长：{30分钟/45分钟/60分钟}**
**访谈方式：{线上视频/电话/线下面对面}**
**核心假设/关注点：{你希望验证或了解的关键问题}**

**请输出以下内容：**

1. 访谈准备
   - 受访者筛选标准（必选条件/加分条件/排除条件）
   - 访谈前需确认的事项清单
   - 开场白话术（建立信任、说明目的、录音许可）

2. 第一阶段：探索（约30%时间）
   - 破冰问题（1-2个，让受访者放松）
   - 开放式探索问题（3-5个）
   - 目的：了解受访者的整体背景和使用情境
   - 每个问题附追问方向

3. 第二阶段：验证（约40%时间）
   - 核心验证问题（5-8个）
   - 目的：验证预设假设，了解具体行为和态度
   - 每个问题附：追问话术、观察要点
   - 关键问题标注⭐

4. 第三阶段：深挖（约20%时间）
   - 深度追问问题（3-5个）
   - 目的：挖掘隐性需求、情感动机、极端场景
   - 使用"5Why"追问技巧
   - 每个问题附追问路径

5. 结束阶段（约10%时间）
   - 补充问题（有没有我们没问到但你觉得重要的）
   - 感谢与后续安排
   - 是否愿意参与后续调研

6. 访谈注意事项
   - 需要避免的引导性问题示例
   - 沉默处理技巧
   - 偏题时的拉回话术

**约束：**
- 问题必须开放式的，避免是非题
- 不得使用引导性语言（如"你是不是觉得..."）
- 每个问题必须附追问方向，确保可深挖
- 时间分配要合理，核心问题放在受访者精力最集中的阶段
- 访谈大纲总问题数控制在15-20个，避免信息过载
- 标注每个问题的预估用时

**输出格式：**
## 用户访谈大纲：{研究主题}
### 1. 访谈准备
### 2. 第一阶段：探索（约XX分钟）
### 3. 第二阶段：验证（约XX分钟）
### 4. 第三阶段：深挖（约XX分钟）
### 5. 结束阶段（约XX分钟）
### 6. 访谈注意事项

## 五、产品路线图规划

### 适用场景
<small style="color:#aaa">季度/半年度产品规划、OKR制定、跨团队对齐目标，需要基于商业目标和技术约束制定可落地的路线图。</small>

<small style="color:#888">提示词：</small>

**你是一位产品战略顾问，擅长基于商业目标和技术约束制定可执行的产品路线图，确保团队聚焦高价值事项。**

**请根据以下信息制定产品路线图：**

**产品名称：{产品名称}**
**产品阶段：{从0到1/成长期/成熟期/转型期}**
**规划周期：{Q1-Q2/Q1-Q4/年度}**
**商业目标：{营收目标/用户增长/留存提升/市场拓展}**
**技术约束：{团队规模/技术债务/基础设施限制}**
**当前产品状态：{核心指标现状、已有功能、已知问题}**
**利益相关方诉求：{业务方/管理层/用户/销售的关键诉求}**

**请输出以下内容：**

1. 战略对齐
   - 商业目标拆解为产品目标
   - 产品目标与OKR对齐
   - 关键假设清单（路线图成立的前提条件）

2. 主题规划
   - 按季度划分主题（每个季度1-2个核心主题）
   - 主题选择的理由（与商业目标的关联）
   - 主题之间的逻辑递进关系

3. 需求池与优先级排序
   - 列出所有候选需求
   - 使用 RICE 框架打分（Reach × Impact × Confidence / Effort）
   - 排序结果及排序逻辑说明

4. 季度路线图
   - 每季度包含：主题、核心功能、预期成果、关键里程碑
   - 依赖关系标注（跨团队依赖、技术依赖）
   - 风险标注（高/中/低）

5. 资源与节奏
   - 团队配置建议
   - 发布节奏（大版本/小版本/热修复）
   - 关键节点时间线

6. 度量与调整机制
   - 每个主题对应的成功指标
   - 路线图健康度检查频率
   - 调整触发条件（什么情况下需要重新评估路线图）

**约束：**
- 每季度主题不超过2个，避免资源分散
- 优先级排序必须使用量化框架，不能仅凭直觉
- 必须考虑技术债务的偿还，不能全部堆新功能
- 路线图要留有20%的弹性空间应对变化
- 依赖关系必须明确标注，避免后期阻塞
- 每个功能需标注预期上线时间和验证指标

**输出格式：**
## 产品路线图：{产品名称}（{规划周期}）
### 1. 战略对齐
### 2. 主题规划
### 3. 需求池与优先级排序
### 4. 季度路线图
### 5. 资源与节奏
### 6. 度量与调整机制

## 六、数据指标体系

### 适用场景
<small style="color:#aaa">产品数据体系建设、增长指标定义、埋点方案设计，需要从北极星指标到二级指标建立完整的数据监控体系。</small>

<small style="color:#888">提示词：</small>

**你是一位数据驱动产品专家，擅长设计从北极星指标到二级指标的完整数据体系，并输出可落地的埋点方案。**

**请根据以下信息设计数据指标体系：**

**产品名称：{产品名称}**
**产品类型：{SaaS/电商/社交/内容/工具}**
**产品阶段：{冷启动/增长期/成熟期/衰退期}**
**核心商业模式：{广告/订阅/交易/增值服务}**
**当前业务目标：{用户增长/活跃提升/付费转化/留存改善}**
**已有数据基础：{有埋点体系/部分埋点/无埋点}**

**请输出以下内容：**

1. 北极星指标
   - 指标定义（精确计算公式）
   - 选择理由（为什么这个指标最能反映产品价值）
   - 当前基线值（如有）与目标值
   - 指标局限性说明

2. 一级指标（3-5个）
   - 每个指标的定义、计算公式
   - 与北极星指标的逻辑关系
   - 负责团队/角色
   - 监控频率（实时/日/周/月）

3. 二级指标（每个一级指标拆解2-4个）
   - 每个指标的定义、计算公式
   - 与一级指标的拆解关系
   - 可操作的优化方向

4. 指标拆解树
   - 北极星 → 一级 → 二级的完整拆解路径
   - 各指标间的因果/相关关系
   - 关键漏斗及转化率

5. 埋点方案
   - 事件埋点清单（事件名、触发时机、属性字段、属性值类型）
   - 页面埋点清单（页面名、关键行为、来源追踪）
   - 用户属性埋点（需要采集的用户维度信息）
   - 埋点优先级排序（P0必埋/P1重要/P2补充）

6. 数据看板设计
   - 核心看板布局（日看板/周报看板/月度复盘看板）
   - 每个看板包含的关键图表
   - 告警规则（异常波动的阈值设定）

**约束：**
- 北极星指标只能有1个，必须反映用户获得的核心价值
- 每个指标必须有明确的计算公式，避免歧义
- 埋点事件命名遵循统一规范（如 object_action 格式）
- 埋点方案必须考虑数据采集的隐私合规要求
- 指标体系要覆盖全链路，不能只看结果不看过程
- 二级指标必须可操作，能直接指导产品优化动作

**输出格式：**
## 数据指标体系：{产品名称}
### 1. 北极星指标
### 2. 一级指标
### 3. 二级指标
### 4. 指标拆解树
### 5. 埋点方案
### 6. 数据看板设计

## 七、A/B 测试设计

### 适用场景
<small style="color:#aaa">功能优化验证、UI方案对比、定价策略测试、增长实验，需要设计科学严谨的A/B测试方案。</small>

<small style="color:#888">提示词：</small>

**你是一位增长产品专家，擅长设计科学严谨的A/B测试方案，确保实验结果可信、结论可执行。**

**请根据以下信息设计A/B测试方案：**

**产品名称：{产品名称}**
**测试对象：{页面/功能/流程/定价/推送策略}**
**当前问题：{转化率低/流失率高/点击率差/...}**
**优化方向：{UI改版/文案优化/流程简化/定价调整}**
**日活/流量：{日均UV}**
**当前核心指标基线：{当前转化率/点击率/...}**
**可接受的最小提升幅度：{相对提升X%}**

**请输出以下内容：**

1. 实验假设
   - 假设陈述：如果我们{做某改变}，那么{某指标}将{提升/降低}X%，因为{原因}**
   - 假设的理论依据
   - 预期影响方向及幅度

2. 实验分组设计
   - 对照组（A组）：当前方案描述
   - 实验组（B组）：新方案描述
   - 如需多组：各组差异说明
   - 流量分配比例及理由

3. 样本量计算
   - 基线转化率
   - 最小可检测效应（MDE）
   - 统计显著性水平（α，默认0.05）
   - 统计功效（1-β，默认0.8）
   - 计算所得每组最小样本量
   - 预计实验时长（基于当前流量估算）

4. 指标定义
   - 核心指标（OEC，Overall Evaluation Criterion）：1个，决定实验成败
   - 辅助指标：2-3个，帮助理解实验影响
   - 护栏指标：1-2个，确保实验不产生负面影响
   - 每个指标的定义、计算公式、预期变化方向

5. 实验执行方案
   - 实验上线前检查清单
   - 灰度发布策略（先5%→20%→50%→100%）
   - 数据监控频率
   - 提前终止条件（护栏指标恶化的阈值）

6. 结果评估标准
   - 统计显著性判定标准
   - 实际显著性判定标准（业务意义）
   - 辛普森悖论排查（按细分群体检查）
   - 新奇效应排查（排除初期新鲜感影响）
   - 决策规则：显著正向→全量；显著负向→回退；不显著→延长或放弃

**约束：**
- 实验假设必须可证伪
- 核心指标只能有1个，避免多指标导致结论模糊
- 样本量必须基于统计公式计算，不能拍脑袋
- 必须设置护栏指标，防止优化一个指标却损害另一个
- 实验时长至少覆盖一个完整周期（如包含周末/工作日）
- 必须考虑溢出效应和网络效应的影响

**输出格式：**
## A/B测试方案：{测试名称}
### 1. 实验假设
### 2. 实验分组设计
### 3. 样本量计算
### 4. 指标定义
### 5. 实验执行方案
### 6. 结果评估标准

## 八、产品复盘

### 适用场景
<small style="color:#aaa">项目上线后复盘、季度业务回顾、功能迭代总结，需要结构化梳理经验教训并形成改进行动。</small>

<small style="color:#888">提示词：</small>

**你是一位产品复盘教练，擅长引导结构化复盘，帮助团队从项目中提炼经验、形成可落地的改进方案。**

**请根据以下信息进行产品复盘：**

**产品/项目名称：{名称}**
**复盘周期/范围：{Q1/某次大版本/某个功能/某次活动}**
**原始目标：{上线前设定的目标和指标}**
**实际结果：{核心指标的实际达成情况}**
**项目时间线：{启动时间、关键节点、上线时间}**
**参与角色：{产品/设计/开发/测试/运营}**
**已知问题：{过程中暴露的问题或意外}**

**请输出以下内容：**

1. 目标回顾
   - 原始目标清单（量化指标+定性目标）
   - 目标达成情况总览（达标/未达标/超额完成）
   - 目标合理性反思（目标设定是否合理，有无偏差）

2. 结果分析
   - 核心指标对比表（目标值 vs 实际值 vs 差异%）
   - 达成目标的关键成功因素（3-5条）
   - 未达成目标的根因分析（使用5Why法深挖）
   - 意外收获与意外损失

3. 过程回顾
   - 时间线关键节点回顾
   - 协作效率评估（跨团队沟通、决策速度、阻塞点）
   - 资源使用效率（人力是否合理分配）
   - 风险管理评估（风险是否被提前识别和应对）

4. 经验提炼
   - 做得好的（Continue）：值得继续保持的做法，3-5条
   - 做得不好的（Stop）：需要停止或改进的做法，3-5条
   - 应该开始做的（Start）：新的改进建议，3-5条
   - 每条经验附具体场景描述，避免泛泛而谈

5. 行动改进
   - 改进项清单（具体行动、负责人、截止时间、验收标准）
   - 按优先级排序（P0立即执行/P1本季度/P2下季度）
   - 需要跨团队协作的改进项标注

6. 知识沉淀
   - 本项目产出的可复用资产（文档/模板/工具/组件）
   - 对其他团队/项目的借鉴意义
   - 需要更新的流程或规范

**约束：**
- 复盘必须对事不对人，避免归因于个人
- 根因分析必须至少追问3层Why，不能停留在表面
- 经验提炼必须具体，避免"加强沟通"等空话，改为"需求评审后24小时内输出会议纪要并同步相关方"
- 行动改进项必须符合SMART原则
- 不得只报喜不报忧，失败经验比成功经验更有价值
- 目标合理性反思是必选项，很多时候问题出在目标设定阶段

**输出格式：**
## 产品复盘：{项目名称}
### 1. 目标回顾
### 2. 结果分析
### 3. 过程回顾
### 4. 经验提炼
### 5. 行动改进
### 6. 知识沉淀
