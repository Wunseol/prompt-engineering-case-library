## 一、测试策略与规划

### 7.1 测试策略制定

<small style="color:#888">适用场景：需要为项目制定系统化的测试策略，包括测试金字塔分层、工具选型、覆盖率目标、数据策略、CI/CD 集成等。适用于新项目启动、现有项目测试补全、CI/CD 流水线测试阶段设计。</small>

**你是一位测试架构师。请为以下项目制定完整的测试策略：[项目描述，包括技术栈、团队规模、发布频率]。请按照以下结构输出：**

**一、风险分析。识别项目中的质量风险，按以下维度分类：业务风险（核心流程失败/资金损失/数据泄露）| 技术风险（并发/集成/性能/安全）| 运营风险（配置错误/部署失败/监控缺失）。输出：风险项 | 可能性 | 影响度 | 风险等级 | 对应测试类型。**

**二、测试金字塔设计。基于风险分析，设计分层测试策略：单元测试（范围/框架/Mock 策略/覆盖率目标）| 集成测试（范围/框架/环境策略/覆盖率目标）| E2E 测试（范围/框架/数据策略/关键路径）| 性能测试（基准/负载/压力/稳定性）| 安全测试（SAST/DAST/依赖扫描）。每层必须说明：为什么测、测什么、怎么测。**

**三、工具选型。为每层测试推荐工具，输出表格：测试层 | 工具名称 | 版本 | 选型理由 | 替代方案 | 学习成本。工具必须与项目技术栈兼容。**

**四、分层覆盖率目标。定义各层覆盖率目标及计算方式：单元测试行覆盖率 | 单元测试分支覆盖率 | 集成测试 API 覆盖率 | E2E 核心路径覆盖率 | 整体质量门禁标准。目标必须基于项目阶段给出（MVP/成长期/成熟期分别不同）。**

**五、测试数据策略。设计测试数据管理方案：数据生成方式（Factory/Fixture/Faker）| 数据隔离策略 | 敏感数据脱敏 | 数据清理策略 | 测试环境数据同步。**

**六、CI/CD 集成。设计测试在流水线中的执行策略：提交阶段（快速反馈测试子集）| 合并阶段（完整单元+集成测试）| 部署前阶段（E2E+性能测试）| 生产阶段（冒烟测试+监控）。每阶段定义：执行时间预算 | 失败策略 | 通知机制。**

**约束：**
- 测试策略必须基于风险驱动，不能平均用力
- 覆盖率目标必须可量化、可验证，不能写"尽量高"
- 工具选型必须考虑团队现有技能和项目技术栈
- CI/CD 各阶段必须有明确的时间预算
- 测试数据策略必须考虑数据隐私合规

**输出格式：**
## 1. 风险分析
## 2. 测试金字塔设计
## 3. 工具选型
## 4. 分层覆盖率目标
## 5. 测试数据策略
## 6. CI/CD 集成

## 二、代码审查与重构

### 7.5 深度代码审查

<small style="color:#888">适用场景：全量代码审查，逐行审查架构设计与逻辑正确性，识别需要重构或优化的部分。</small>

**Role:** 资深代码审查工程师，精通架构设计与代码质量分析。

**Task:** 对以下代码进行全面深度审查，从头到尾逐行核对各模块的架构设计与逻辑正确性，识别需要重构或优化的部分，检查模块之间的协作是否正常运行，并整理优化建议。

**[粘贴待审查代码或模块清单]**

**Constraints:**
- 逐行审查，不可跳过任何模块
- 同时关注架构设计与逻辑正确性两个层面
- 检查模块间协作是否正常运行
- 识别需要重构或优化的部分并系统整理
- 全面排查潜在 Bug

**Output Format:**
按模块输出审查结果，每个模块包含：架构设计评估 | 逻辑正确性评估 | 模块协作情况 | 需重构或优化点 | 发现的 Bug 清单。最后汇总整体优化建议。

---

### 7.6 代码重构

<small style="color:#888">适用场景：代码存在重复、耦合度高、职责不清等质量问题，需要提升可读性、可维护性和可扩展性。</small>

**请重构以下代码，提升可读性、可维护性和可扩展性：**

**[粘贴代码]**

**重构要求：**
- 遵循 [SOLID / DRY / KISS] 原则
- 提取重复代码为公共方法
- 优化函数职责，确保单一职责
- 添加必要的注释
- 保持功能不变，不改变对外接口

---

### 7.7 性能优化

<small style="color:#888">适用场景：代码存在性能瓶颈，需要针对性分析与优化并对比优化前后差异。</small>

**以下代码存在性能问题，请帮我分析和优化：**

**[粘贴代码]**

**当前瓶颈：[描述性能问题，如"接口响应慢"、"内存占用高"、"加载时间长"等]**

**优化要求：**
- 先分析性能瓶颈所在
- 给出优化方案及预期效果
- 提供优化后的代码
- 对比优化前后的差异

<small style="color:#888">填写说明：尽可能描述具体的性能指标（如"响应时间从3秒降到500ms以内"），AI 会更有针对性地优化。</small>

---

### 7.8 代码审查 Code Review

<small style="color:#888">适用场景：代码提交前的质量审查，或对他人代码的评审，按严重程度分级列出问题。</small>

**请对以下代码进行 Code Review，从以下维度给出改进建议：**

**[粘贴代码]**

**审查维度：**
1. 代码规范：命名、格式、注释是否规范
2. 安全性：是否存在安全漏洞（SQL注入、XSS等）
3. 性能：是否存在明显的性能问题
4. 可维护性：是否易于理解和修改
5. 边界处理：异常情况和边界条件是否处理
6. 最佳实践：是否符合语言/框架的最佳实践

**请按严重程度（高/中/低）分级列出所有问题，并给出修改建议。**

## 三、测试执行与自动化

### 7.9 标准化测试流程

<small style="color:#888">适用场景：系统测试全流程，从测试需求到测试报告的完整闭环。</small>

**Role:** 测试工程师，负责系统测试全流程规划与执行。

**Task:** 对 {系统/模块名称} 执行标准化测试流程，依次完成：测试需求文档 → 测试计划文档 → 测试用例编写与评审 → 测试执行 → Bug 提交与跟踪 → Bug 修复后回归测试 → 测试报告编写。

**Constraints:**
- 严格按流程顺序执行，前一阶段完成后再进入下一阶段
- 测试用例需经过评审后方可执行
- 提交的 Bug 需持续跟踪直至闭环
- 修复 Bug 后必须再次测试验证
- 若任务较多，可先输出 Bug 清单，后续等待指令指导修复

**Output Format:**
依次输出：1. 测试需求文档 | 2. 测试计划文档 | 3. 测试用例（含评审记录）| 4. 测试执行记录 | 5. Bug 清单与跟踪台账 | 6. 回归测试结果 | 7. 测试报告

---

### 7.10 多轮迭代回归测试

<small style="color:#888">适用场景：回归测试与缺陷闭环，专项复测与功能巡检结合，确保不产生衍生问题。</small>

**针对第一轮标记的待修复 Bug 进行专项复测，逐一确认修复有效性。同步巡检系统各项核心功能，关注是否出现衍生问题。核对所有已修复问题，逐条验证 Bug 是否闭环；同时复测第一轮涉及的全部系统功能，检查是否产生新问题、功能退化。全部测试完成后，补充完善整体测试报告。**

---

### 7.11 全面系统测试（纯净初始化）

<small style="color:#888">适用场景：系统级集成测试，纯净初始化环境下完整执行核心业务流程验证全部功能模块。</small>

**清空所有旧数据、历史记录、状态数据、记忆数据，重置所有工作 Agent 运行状态，确保完全纯净的初始化环境。完整执行一个核心业务流程（覆盖所有关键功能模块），验证所有功能模块、记忆引擎、前后端数据交互、Agent 隔离等。请输出系统级集成测试报告，覆盖功能、记忆、数据交互、隔离四大维度。**

---

### 7.12 前后端联调测试

<small style="color:#888">适用场景：前后端接口测试，全流程联调与字段映射一致性校验。</small>

**Role:** 前后端联调测试工程师，负责接口联调与数据一致性校验。

**Task:** 启动前端服务，开展前后端全流程联调测试，测试前端与后端交互的全部接口，覆盖请求、响应、异常、边界场景；逐项校验前后端字段映射是否完全一致。

**Constraints:**
- 覆盖全部前后端交互接口
- 测试场景必须包含请求、响应、异常、边界四类
- 字段映射校验需逐项核对：字段名、字段类型、是否非空、枚举值、长度规则
- 字段映射必须完全一致，任何不一致都需记录

**Output Format:**
1. 前后端联调测试报告（含接口清单、测试场景、执行结果、异常记录）
2. 字段映射核对表：| 接口名 | 字段名 | 前端类型 | 后端类型 | 非空一致 | 枚举一致 | 长度规则一致 | 是否通过 |

---

### 7.13 Bug 深度修复

<small style="color:#888">适用场景：Bug 根因分析与修复，详细排查原因并再次全面测试。</small>

**Role:** Bug 修复工程师，负责根因分析与修复验证。

**Task:** 详细排查测试中遇到的 Bug 根因，尝试修复 Bug，修复后再次进行全面测试，并将测试报告输出为 Markdown 文件。

**Constraints:**
- 必须定位 Bug 根因，不能仅修复表面现象
- 修复后需进行全面回归测试，避免引入新问题
- 测试报告需覆盖修复前后的对比验证

**Output Format:**
输出 Markdown 文件，包含：1. Bug 根因分析（每个 Bug 的原因定位）| 2. 修复方案与改动内容 | 3. 修复后全面测试报告 | 4. 验证结果与结论

## 四、AI 系统评估与监控

### 7.14 ISO25010 质量特性测试

<small style="color:#888">适用场景：全面质量评估，依据 ISO25010 软件质量六大标准开展全维度质量闭环测试。</small>

**Role:** 软件质量评估专家，精通 ISO25010 质量模型。

**Task:** 严格依据 ISO25010 软件质量六大标准，对 {系统/模块名称} 开展全维度质量闭环测试，覆盖六大特性：1.功能性 2.性能效率 3.可靠性/鲁棒性 4.易用性 5.可维护性 6.可移植性。为每个特性输出测试提示词、测试点清单与执行方案，并汇总成质量评估报告。

**Constraints:**
- 严格依据 ISO25010 标准，不遗漏六大特性中的任何一个
- 每个特性需有专属测试提示词
- 每个特性需输出测试点清单与执行方案
- 最终需汇总为统一的质量评估报告

**Output Format:**
针对每个质量特性输出：1. 测试提示词 | 2. 测试点清单 | 3. 执行方案。最后汇总输出：质量评估报告（含各特性评分、问题清单、改进建议、整体质量结论）。

**Task:** 通过网络搜索业界对 Agent Eval 系统的相关研究，编写 Agent Eval 系统设计文档，并将现有质量评估体系重构为标准化的 Agent Eval 系统。请输出设计文档与重构改造清单。

**Constraints:**
- 设计需基于业界对 Agent Eval 系统的研究成果
- 评估体系需具备完整性与可落地性
- 重构改造清单需明确具体改造项与优先级

**Output Format:**
1. Agent Eval 系统设计文档（含背景研究、架构设计、评估指标体系、评估流程）
2. 重构改造清单：| 改造项 | 当前状态 | 目标状态 | 改造方案 | 优先级 | 预期收益 |

### 7.16 Token 消耗监控

<small style="color:#888">适用场景：性能与成本分析，监控执行核心业务流程的全部 Token 去向。</small>

**Role:** Token 消耗监控分析师，负责大模型调用的成本与去向分析。

**Task:** 在初始化环境下执行 {核心业务流程描述}，监控所有 Token 的消耗情况及每一笔 Token 的去向，包括使用这些 Token 生成的内容，输出为 Markdown 文档记录。

**Constraints:**
- 监控需覆盖全部 Token 消耗，不可遗漏
- 需记录每笔 Token 的去向与生成内容
- 监控数据需支持成本归因分析

**Output Format:**
输出 Markdown 文档，包含：1. 监控环境与初始化说明 | 2. Token 消耗总览（总消耗量、按阶段分布、按调用分布）| 3. Token 去向明细表：| 调用阶段 | Token 用量 | 用途 | 生成内容摘要 | 4. 成本分析与优化建议

### 7.17 测试报告与文档同步

<small style="color:#888">适用场景：测试收尾与归档，汇总测试数据并同步更新至项目知识库，确保测试资产可追溯、可复用。</small>

**Role:** 测试收尾与文档管理工程师，负责测试资产汇总与归档。

**Task:** 全轮次测试完成后，汇总所有测试数据、缺陷统计、模块验收情况，输出正式系统测试报告；将所有测试文档、Bug 台账、优化方案同步更新至项目知识库，确保测试资产可追溯、可复用。

**Constraints:**
- 测试报告需汇总全部轮次的测试数据
- 缺陷统计需完整覆盖所有 Bug 的状态与闭环情况
- 测试资产同步需覆盖：测试文档、Bug 台账、优化方案
- 确保所有测试资产可追溯、可复用

**Output Format:**
1. 正式系统测试报告（含测试概况、执行结果、缺陷统计、模块验收、质量结论）
2. 测试资产同步清单：| 资产类型 | 文档名 | 存放位置 | 更新状态 | 可追溯标识 |
