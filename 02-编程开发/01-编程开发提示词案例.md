# 编程开发提示词案例集

> 本文档整理了 AI 辅助编程开发中的常用提示词模板，按使用场景分类，可直接复制使用或根据实际情况调整。

> **前置说明**：本文档中提示词前缀 `/plan` 和 `/spec` 是特定 AI 编程助手（如 Windsurf、Trae 等）的命令格式，用于区分"规划模式"和"执行模式"。若使用其他 AI 工具（如 Claude、GPT、Copilot 等），请去掉前缀，直接复制提示词正文即可。

## 一、项目规划与需求拆解

### 1.1 需求拆解为文档

```
/plan 我的需求：[填写需求描述]

请将我的需求进行拆解为详细的需求文档（需要分各模块，如果需求太庞大，可以写多个 md 文件），输出 md 文件在 docs/ 下，文件名你定。
```

**适用场景**：将模糊的需求转化为结构化的需求文档，适合项目初期规划阶段。

**填写说明**：`[填写需求描述]` 替换为具体需求，例如"开发一个用户管理系统，包含登录、注册、个人资料修改等功能"

---

### 1.2 制定实施方案

```
/plan docs下有多个模块的需求文档，请写一个具体的实施方案。实施方案不是空中楼阁，是具体的实施步骤，因此步骤的前后顺序非常重要。
```

**适用场景**：在需求文档完成后，制定可落地的执行步骤。

---

### 1.3 根据方案实现代码

```
/spec 请根据该实施方案：[文件名.md]，实现代码。
```

**适用场景**：有明确的实施方案后，让 AI 直接编码实现。

---

## 二、项目文档优化

### 2.1 项目文档体系建设

```
/spec 优化项目文档，拆解检查研究项目结构，统合项目需求文档、实施文档、项目报告。要让我能彻底读懂这个项目的代码，还要让企业项目组的新成员能根据这些项目报告深度了解这个项目。这些文档需要与当前的项目源码深度结合，讲解代码和对应的跳转路径能真的跳转到对应的源码，从而让新人充分了解并具备参与这个项目的能力。
```

**适用场景**：为现有项目补充文档，方便团队协作与新人上手。

---

### 2.2 项目命名与规范优化

```
/spec 检查该项目结构，优化项目命名和代码，并添加 README 和开源协议文件。
```

**适用场景**：项目初始化或规范化阶段，统一命名规范并补充必要文件。

---

## 三、代码调试与Bug修复

### 3.1 错误分析与定位

```
以下代码运行报错，请帮我分析原因并修复：

[粘贴报错信息]

[粘贴相关代码]

请先分析错误原因，再给出修复方案，最后提供修复后的完整代码。
```

**适用场景**：代码运行出错，需要快速定位和修复问题。

**填写说明**：同时提供报错信息和相关代码，AI 能更准确地定位问题。

---

### 3.2 Bug追踪与修复

```
我在 [功能模块] 中发现了一个 Bug：[Bug现象描述]。

预期行为：[描述预期行为]
实际行为：[描述实际行为]
复现步骤：[描述复现步骤]

请帮我分析可能的 Bug 原因，并提供修复方案。
```

**适用场景**：功能表现异常，需要系统性排查和修复。

---

### 3.3 异常处理完善

```
请检查以下代码的异常处理是否完善，补充缺失的异常捕获和错误提示，确保程序在各种边界情况下都不会崩溃：

[粘贴代码]

要求：
- 补充所有可能抛出异常的代码的 try-catch
- 添加用户友好的错误提示信息
- 对关键操作添加回滚机制
- 输出修复后的完整代码
```

**适用场景**：代码缺少异常处理，需要增强健壮性。

## 四、代码重构与性能优化

### 4.1 代码重构

```
请重构以下代码，提升可读性、可维护性和可扩展性：

[粘贴代码]

重构要求：
- 遵循 [SOLID / DRY / KISS] 原则
- 提取重复代码为公共方法
- 优化函数职责，确保单一职责
- 添加必要的注释
- 保持功能不变，不改变对外接口
```

**适用场景**：代码存在重复、耦合度高、职责不清等质量问题。

---

### 4.2 性能优化

```
以下代码存在性能问题，请帮我分析和优化：

[粘贴代码]

当前瓶颈：[描述性能问题，如"接口响应慢"、"内存占用高"、"加载时间长"等]

优化要求：
- 先分析性能瓶颈所在
- 给出优化方案及预期效果
- 提供优化后的代码
- 对比优化前后的差异
```

**适用场景**：代码存在性能瓶颈，需要针对性优化。

**填写说明**：尽可能描述具体的性能指标（如"响应时间从3秒降到500ms以内"），AI 会更有针对性地优化。

---

### 4.3 代码审查

```
请对以下代码进行 Code Review，从以下维度给出改进建议：

[粘贴代码]

审查维度：
1. 代码规范：命名、格式、注释是否规范
2. 安全性：是否存在安全漏洞（SQL注入、XSS等）
3. 性能：是否存在明显的性能问题
4. 可维护性：是否易于理解和修改
5. 边界处理：异常情况和边界条件是否处理
6. 最佳实践：是否符合语言/框架的最佳实践

请按严重程度（高/中/低）分级列出所有问题，并给出修改建议。
```

**适用场景**：代码提交前的质量审查，或对他人代码的评审。

## 五、测试与质量保证

### 5.1 单元测试编写

```
请为以下函数/方法编写完整的单元测试：

[粘贴代码]

要求：
- 使用 [JUnit / pytest / Jest 等测试框架名]
- 覆盖所有正常分支
- 覆盖边界条件（空值、零值、极大值等）
- 覆盖异常情况
- 使用有意义的测试命名（如 test_预期行为_当条件）
- 添加必要的 mock 和 stub
```

**适用场景**：为已有代码补充单元测试，提高代码覆盖率。

---

### 5.2 集成测试编写

```
请为以下模块编写集成测试：

[粘贴相关模块代码或接口定义]

涉及的模块/服务：
- [模块A]：[简要说明]
- [模块B]：[简要说明]

要求：
- 测试模块间的交互是否正确
- 测试数据流转是否完整
- 测试异常场景下的降级和回滚
- 使用测试数据库/内存数据库替代真实数据库
- 清理测试数据，不影响其他测试
```

**适用场景**：验证多个模块协作的正确性。

---

### 5.3 测试用例设计

```
请为以下功能设计测试用例矩阵：

功能描述：[描述功能]
输入参数：[列出参数及取值范围]
业务规则：[列出关键业务规则]

请使用等价类划分和边界值分析法，输出以下格式的测试用例表：

| 用例编号 | 用例描述 | 前置条件 | 输入 | 预期结果 | 优先级 |
```

**适用场景**：功能开发前系统化设计测试用例，避免遗漏。

## 六、API与数据库设计

### 6.1 API接口设计

```
请为以下业务场景设计 RESTful API 接口：

业务场景：[描述业务场景]
涉及实体：[列出主要实体]
核心功能：[列出核心操作]

设计要求：
- 遵循 RESTful 规范
- 合理使用 HTTP 方法和状态码
- 设计统一的请求/响应格式
- 考虑分页、排序、过滤
- 考虑接口版本管理
- 列出每个接口的 URL、方法、请求参数、响应格式、错误码
```

**适用场景**：前后端分离项目，设计标准化 API 接口。

---

### 6.2 数据库设计

```
请为以下业务场景设计数据库：

业务场景：[描述业务场景]
核心实体：[列出主要实体和关系]

设计要求：
- 给出 ER 图描述（实体、属性、关系）
- 设计表结构（表名、字段名、类型、约束、索引）
- 考虑数据量增长，合理设计索引
- 考虑软删除、创建时间、更新时间等公共字段
- 考虑数据一致性和并发安全
- 输出建表 SQL 语句
```

**适用场景**：新项目或新模块的数据库设计。

请为以下项目编写部署配置：

部署目标：[Docker / 云服务 / VPS]

## 九、源码学习与逆向分析

### 9.1 学习开源项目源码

```
/plan 当前目录下有一份[项目名]的源码，我需要学习这份源码。请你分析拆解这份源码，让我充分了解它的设计、结构、开发思想等，帮我从零开始学习这份源码，直到我有基于它设计其他项目或继续开发的能力。解析透彻，小白也能学会。

请将我的需求进行拆解为详细的需求文档（需要分各模块，如果你觉得需求太庞大了，可以写多个md文件），输出md文件在docs/下，文件名你定。
```

**适用场景**：学习复杂开源项目，快速掌握其架构和设计思想。

---

### 9.2 专项技术深入学习

```
/spec 我发现缺少[技术名]的学习文档，这个项目是我们研究项目之一，比较重要，需要专注优化这份学习文档。要详细，不仅要让人学会怎么用，还要讲解这个项目的结构、如何二次开发等深入了解。

学习文档要求：
- 具体参照官方技术文档
- 学习前后顺序、时效性、严谨性非常重要
- 检查开源项目最近的更新维护情况
- 按官方推荐来写，可能随时间变化的技术需标注
```

**适用场景**：对特定技术进行深度学习和文档化。

## 十、科技树与技术栈管理

### 10.1 构建技术栈清单

```
/plan 我们是一家[公司类型描述]，业务是[业务描述]。根据公司情况构建科技树，不同技术方向（按方向确定对应技术清单，方向你来确定），生成各方向的技术栈清单和学习大纲文档。

优化要求：
- 每个方向的学习大纲专注于要学习的技术
- 不仅罗列技术栈，还需有详细的学习路径（从小白到大牛）
- 整理大纲内容，不要写能力等级体系和学习路径总览
- 不要分阶段，直接队列排列，后续以技术栈名称作为标题
- 删除多余空行，学习资源只放官方链接，不要纸质书籍
- 相似技术栈用高一级标题合并
```

**适用场景**：初创团队或新部门搭建技术体系时使用。

---

### 10.2 技术栈持续优化

```
/plan 优化并完善各个方向的技术栈清单，我们尤其关注开源项目、软件、框架、技术。每个方向增加主流的开源项目技术框架，然后以各方向技术栈清单为基准，在各方向文件夹下写具体的学习文档。

学习文档要求：
- 不是空中楼阁，要具体参照官方技术文档
- 学习前后顺序、时效性、严谨性等都非常重要
- 检查开源项目最近的更新维护情况
- 按官方推荐来写，可能随时间变化的技术需标注
```

**适用场景**：定期更新和优化团队技术栈清单，保持时效性。

---

### 10.3 学习文档深度优化

```
/plan 对[指定方向]的学习文档进行全面检查与优化。重点关注：

1. **内容时效性**：检查开源项目最近的更新维护情况，将最新动态整合到文档中
2. **信息严谨性**：严格按官方推荐规范撰写，可能随时间变化的内容明确标注
3. **逻辑顺序**：优化组织结构和内容呈现顺序，确保知识体系连贯
4. **内容准确性**：全面核对技术描述、代码示例和配置说明
5. **版本兼容性**：明确标注功能差异和兼容性要求

处理完成后，提供详细的优化报告。
```

**适用场景**：定期审视和优化学习文档质量。

## 十二、文档管理规范

### 12.1 修改优先级规则

> **重要规则**：以后做修改必须严格按照以下顺序：
> 1. 先改技术栈清单
> 2. 再改学习文档
> 3. 再改案例文档（案例文档移到最后）
> 4. 最后加上更新时间和维护者

### 12.2 上下文压缩

```
/spec 把 specs 里长上下文压缩成摘要，消掉冗余，只留关键信息，没用的文件删掉。
```

**适用场景**：项目进行到中后期，上下文过长时压缩精简。

## 十三、使用建议

| 建议项 | 说明 |
|--------|------|
| 分窗口操作 | 一个窗口只做一个任务，串行执行不要并行 |
| 模型选择 | 复杂任务选强推理模型（如 o3、Claude Opus），常规任务选性价比模型，简单任务选轻量模型 |
| 先规划后执行 | 先用 `/plan` 规划，确认后再用 `/spec` 执行 |
| 提供充分上下文 | 粘贴相关代码、报错信息、文件路径，AI 能更准确理解需求 |
| 迭代优化 | 一次生成不满意，追问细节或调整要求后重新生成 |
| 保持时效性 | 定期检查开源项目更新情况，更新到文档中 |
| 注重严谨性 | 按官方推荐来写，可能过时的内容要标注 |
| Agent 设计原则 | 定义清晰的职责边界、工具调用格式、安全检查点和错误处理流程 |

## 十四、AI Agent 开发

### 14.1 Agent 系统提示词设计

```
/plan 设计一个 {Agent名称} Agent 的系统提示词。

Agent 的核心职责：{职责描述}
可用工具：{工具列表}
目标用户：{目标用户}

系统提示词需要包含：
1. 角色身份定义
2. 核心行为准则
3. 工具调用规范（格式、顺序、错误处理）
4. 安全约束
5. 输出格式要求
6. 错误处理指南
```

**适用场景**：从零设计一个 AI Agent 的系统提示词，参考 `AI编程助手系统提示词案例.md` 中的模式。

### 14.2 Agent 工作流编排

```
/plan 设计以下 Agent 工作流：

任务：{任务描述}
参与 Agent：{Agent列表}
数据流：{数据在 Agent 间如何传递}

输出格式：
1. 工作流步骤图（用文本描述）
2. 每个 Agent 的职责和输入/输出
3. 异常处理策略
4. 性能优化建议

约束：
- 每个 Agent 职责单一，不要设计全能 Agent
- Agent 间通过结构化数据（JSON）通信
- 包含重试和回退机制
- 关键节点需要人工审核
```

**适用场景**：设计多 Agent 协作工作流，如"研究 Agent → 写作 Agent → 审核 Agent"。

### 14.3 Agent 安全与防护

```
/plan 为以下 Agent 设计安全防护策略：

Agent 名称：{名称}
Agent 权限：{可执行的操作}
敏感数据：{涉及的数据类型}

需要覆盖：
1. 输入验证：如何过滤恶意输入
2. 权限控制：操作是否需要确认
3. 输出审查：如何防止泄露敏感信息
4. 目标漂移检测：如何检测 Agent 偏离了原始目标
5. 工具调用限制：单次对话最大调用次数
6. 回退策略：出错时如何恢复

输出为 Markdown 文档。
```

**适用场景**：Agent 安全设计，防范供应链攻击、目标漂移、提示注入等风险。

### 14.4 Agentic Coder（计划优先编码代理）

```
你是一个智能编码代理，必须先规划再编码。

## 工作流程
1. **分析请求**：理解用户的需求和上下文
2. **搜索代码**：使用 codebase_search 查找相关代码
3. **制定计划**：列出具体的修改步骤（不执行）
4. **等待确认**：展示计划，等用户确认后再执行
5. **分步执行**：按计划逐步修改代码
6. **验证结果**：运行测试确认修改正确

## 安全检查清单
- ☐ 不修改用户未提及的文件
- ☐ 不引入安全漏洞（SQL注入、XSS等）
- ☐ 不暴露敏感信息
- ☐ 保持代码风格一致
- ☐ 复杂修改前展示计划

用户请求：{请求内容}
```

**适用场景**：构建安全可靠的编码 Agent，强调"先规划后执行"的工作模式。

### 14.5 Multi-Agent 协调器

```
你是一个多 Agent 协调器，负责将复杂任务分解并委派给专业 Agent。

## 可用 Agent
| Agent | 专长 | 适用任务 |
|-------|------|----------|
| Researcher | 信息搜索和分析 | 数据收集、竞品分析、文献综述 |
| Coder | 代码编写和调试 | 编码、重构、Bug修复 |
| Reviewer | 质量审查 | 代码审查、文档审查、安全审计 |
| Writer | 内容创作 | 文档撰写、报告生成 |

## 工作原则
1. 将复杂任务拆分为子任务
2. 每个子任务委派给最合适的 Agent
3. 并行执行独立的子任务
4. 汇总结果后进行最终审查
5. 如果某步失败，自动重试或切换策略

## 状态追踪
对每个子任务，跟踪：
- 状态：pending → in_progress → completed/failed
- 负责Agent：{agent_name}
- 结果摘要：{result_summary}

用户任务：{任务描述}
```

**适用场景**：复杂项目需要多个专业 Agent 协作完成的场景。
