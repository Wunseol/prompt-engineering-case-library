## 一、Vibe Coding 核心理念

### 1.1 Vibe Coding 起源与核心理念

<small style="color:#888">适用场景：理解 Vibe Coding 的本质和适用边界。</small>

**请解释 Vibe Coding 的起源、核心理念、与传统编程的差异，并分析其适用场景与不适用场景。要求包含：起源背景（Andrej Karpathy 2025 年提出）、核心理念（自然语言意图驱动、AI 生成代码、人机协作）、两种实践模式（纯粹模式：完全信任 AI 输出；增强模式：人机协作、人工审核）、适用场景（原型开发、快速验证、个人项目、学习探索）、不适用场景（生产关键系统、合规要求高的场景、性能敏感场景）、风险与缓解措施。输出格式：## 1. 起源背景 ## 2. 核心理念 ## 3. 实践模式对比 ## 4. 适用场景分析 ## 5. 风险与缓解**

### 1.2 Spec-Driven Development 四步法

<small style="color:#888">适用场景：将模糊需求转化为可执行的规范驱动开发流程。</small>

**作为 Spec-Driven Development 架构师，请将以下产品构想转化为完整的开发规格包：[描述你的产品/功能想法]。严格按照以下四步执行：第一步 Mission 使命声明（用一句话定义项目存在的理由，用一段话定义可量化的成功标准）；第二步 Tech Stack 技术栈决策（列出每层技术选择及理由，每个选择必须说明"为什么选它而不选替代方案"）；第三步 Roadmap 路线图（拆解为不超过 4 个里程碑，每个里程碑包含名称、目标、交付物清单、预估工期、依赖关系）；第四步 Requirements 需求规格（按 MoSCoW 优先级分类：Must/Should/Could/Won't Have，每条需求包含 ID、描述、验收标准、关联里程碑）。约束：Mission 必须在 50 字以内且包含至少 1 个量化指标；每个里程碑交付物必须可演示；每条需求必须有明确的验收标准，不得使用"友好""高效"等模糊词。输出格式：## Mission ## Tech Stack ## Roadmap ## Requirements**

### 1.3 Plan 模式 vs Spec 模式 vs Agent 模式对比

<small style="color:#888">适用场景：根据任务复杂度选择合适的工作模式。</small>

**请对比以下三种 AI 编程工作模式的差异、适用场景与最佳实践：Plan 模式（先规划再执行，适合复杂变更）、Spec 模式（规格驱动开发，适合新功能/新模块）、Agent 模式（自主执行，适合重复性/探索性任务）。对每种模式输出：模式定义、核心工作流、适用任务类型、不适用任务类型、最佳实践要点、风险与防范。最终给出模式选择决策表：任务特征 | 推荐模式 | 理由。约束：对比必须基于具体任务场景，不得泛泛而谈；每种模式必须给出至少 2 个具体适用案例；决策表必须覆盖简单修改、新功能开发、架构重构、Bug 修复、文档编写五类任务。输出格式：## 1. Plan 模式 ## 2. Spec 模式 ## 3. Agent 模式 ## 4. 模式选择决策表**

### 1.4 Agentic Coder 工作流

<small style="color:#888">适用场景：构建安全可靠的编码 Agent，强调"先规划后执行"。</small>

**作为智能编码代理，必须遵循"先规划后编码"的工作流程。工作流程：1. 分析请求（理解用户需求和上下文）；2. 搜索代码（使用代码库搜索查找相关代码）；3. 制定计划（列出具体的修改步骤，不执行）；4. 等待确认（展示计划，等用户确认后再执行）；5. 分步执行（按计划逐步修改代码）；6. 验证结果（运行测试确认修改正确）。安全检查清单：☐ 不修改用户未提及的文件；☐ 不引入安全漏洞（SQL 注入、XSS 等）；☐ 不暴露敏感信息；☐ 保持代码风格一致；☐ 复杂修改前展示计划。约束：每次只处理一个修改请求；修改前必须先阅读相关文件理解上下文；每步修改必须可独立验证；如果引入 Linter 错误必须立即修复，同一文件修复不超过 3 次。用户请求：[填写请求内容]**

### 1.5 Vibe Coding 反模式与避坑指南

<small style="color:#888">适用场景：识别并避免 Vibe Coding 常见陷阱。</small>

**请系统化梳理 Vibe Coding 实践中的常见反模式与避坑指南。按以下维度逐一分析：1. 盲目信任反模式（完全接受 AI 输出不审核、不验证）；2. 上下文缺失反模式（未提供充分代码/文档上下文，AI 凭空生成）；3. 范围蔓延反模式（单次对话请求过多功能，导致 AI 失焦）；4. 验证缺失反模式（不写测试、不运行验证、直接上线）；5. 安全忽视反模式（未审查安全漏洞、硬编码密钥、未脱敏）；6. 架构忽视反模式（只关注功能实现，忽略架构设计、技术债务）；7. 文档缺失反模式（不更新文档，代码与文档脱节）。每个反模式输出：反模式描述、典型表现、潜在危害、防范措施、检测方法。约束：每个反模式必须基于真实场景，不得凭空捏造；防范措施必须可执行，不得写"注意安全"等空话；检测方法必须包含具体的检查清单或工具推荐。输出格式：## 1. 盲目信任反模式 ## 2. 上下文缺失反模式 ## 3. 范围蔓延反模式 ## 4. 验证缺失反模式 ## 5. 安全忽视反模式 ## 6. 架构忽视反模式 ## 7. 文档缺失反模式**

### 1.6 人机协作边界设计

<small style="color:#888">适用场景：明确 AI 与人类的职责分工，设计高效协作流程。</small>

**请为以下项目设计 AI 与人类的协作边界与分工方案：[项目描述，包括项目类型、技术栈、团队规模、AI 工具]。按以下维度设计：1. 决策分级（哪些决策可由 AI 自主、哪些需要人工确认、哪些必须人工执行）；2. 任务分类（AI 擅长任务：代码生成、测试编写、文档撰写、代码审查；人类擅长任务：架构决策、需求澄清、安全审查、业务逻辑验证）；3. 协作流程（任务分配 → AI 执行 → 人工审核 → 反馈迭代 → 验收）；4. 检查点设计（关键节点的人工审核清单）；5. 失败回退策略（AI 输出不达标时的人工接管流程）。输出表格：任务类型 | AI 自主度 | 人工审核要求 | 检查点 | 失败回退。约束：决策分级必须基于风险等级（低风险 AI 自主、中风险人工确认、高风险人工执行）；检查点必须具体可操作；失败回退必须包含明确的触发条件。输出格式：## 1. 决策分级 ## 2. 任务分类 ## 3. 协作流程 ## 4. 检查点设计 ## 5. 失败回退策略**

### 1.7 提示词工程在 Vibe Coding 中的角色

<small style="color:#888">适用场景：理解从"写代码"到"写意图"的角色转变。</small>

**请阐述提示词工程在 Vibe Coding 时代的角色转变与实践方法。对比以下两个时代：传统编程时代（开发者写代码、AI 辅助补全）vs Vibe Coding 时代（开发者写意图、AI 生成代码）。分析：1. 开发者角色转变（从代码编写者 → 意图描述者 → 审核者）；2. 核心能力要求变化（从语法记忆 → 架构思维 → 提示词设计 → 验证能力）；3. 提示词工程的新定位（从可选技能 → 核心技能）；4. 实践方法论（意图清晰化、约束明确化、分步骤拆解、增量交付、持续验证）；5. 评估与优化（如何评估提示词效果、如何迭代优化）。约束：分析必须基于实际工作场景，不得泛泛而谈；方法论必须可操作；评估指标必须可量化。输出格式：## 1. 时代对比 ## 2. 角色转变 ## 3. 能力要求 ## 4. 方法论 ## 5. 评估与优化**
