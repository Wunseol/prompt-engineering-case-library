## 一、记忆与上下文管理

### 9.1 记忆系统架构设计

<small style="color:#888">适用场景：长任务的记忆系统设计，解决超长上下文生成的上下文瓶颈与注意力分散问题。</small>

**Role:** 记忆系统架构师

**Task:** 分析、设计与重构优化长任务场景下的记忆系统，解决超长上下文生成过程中的上下文瓶颈，以及大模型在长任务后期注意力机制分散的问题，作为系统中的关键难点。完成实现后进行测试验证，并检查记忆系统效果；根据需求输出需求文档与实施方案，并严格落实实现。检查前后端信息传递是否正确通畅，完成校验后尝试生成大规模任务，期间验证记忆系统是否正常工作。

**Constraints:**
- 聚焦长任务的上下文瓶颈与注意力分散问题
- 输出需包含需求文档、实施方案与测试验证报告
- 实施过程需严格落实设计方案，并验证前后端信息传递通畅性
- 需通过大规模任务执行验证记忆系统效果

**Output Format:**
1. 需求文档（含问题分析与设计目标）
2. 实施方案（含模块拆解与接口设计）
3. 测试验证报告（含前后端联调结果与大规模任务执行结果）

### 9.2 LLM Wiki 架构选型

<small style="color:#888">适用场景：知识管理架构选型，选择 LLM Wiki 作为记忆系统方案，"提前编译知识而非临时检索"。</small>

**Role:** 知识管理架构师

**Task:** 针对 RAG、知识图谱与 LLM Wiki 的记忆系统选型问题，建议采用 LLM Wiki 作为 {项目名称} 的记忆系统方案（可参考业界主流实现与开源项目源码）。后续将为 {项目名称} 设计与实现 LLM Wiki，借鉴业界主流思想并结合自身设计，属于记忆系统的重大技术选型，需详细设计与实现。

**Constraints:**
- 需对比 RAG、知识图谱与 LLM Wiki 三种方案的优劣
- LLM Wiki 核心思想是"提前编译知识，而非临时检索"：传统 RAG 每次查询都从原始文档临时拼凑答案，知识不会积累；LLM Wiki 让 LLM 作为"知识编译器"，将原始资料整理成结构化、可积累的 Markdown Wiki，知识随使用持续增长
- 三层架构需包含：
  - 原始素材层（Raw Sources）：存放不可修改的原始资料，保证溯源性
  - 结构化知识层：由 LLM 维护，生成摘要、概念页、实体页、对比分析等，人类仅审核和引导，确保内容准确
  - Schema 层（规则定义层）：定义文件夹结构、引用规则、问答行为规范、语法检查规则等
- 核心操作流程需覆盖：知识灌入（Ingest）、智能查询（Query）、健康巡检（Lint）、索引维护

**Output Format:**
1. 三种方案对比分析表
2. LLM Wiki 选型理由与适用场景说明
3. 三层架构设计与模块职责说明
4. 核心操作流程与接口定义

### 9.3 短期记忆与长期记忆解耦

<small style="color:#888">适用场景：记忆系统架构对齐业界参考实现，实现短期记忆与长期记忆的解耦设计。</small>

**Role:** 记忆系统架构师

**Task:** 全面梳理项目的上下文管理设计，包括如何组织与裁剪 context，并与业界参考实现进行深度对比。参考业界参考实现，优化上下文管理，实现短期记忆与长期记忆的解耦。

**Constraints:**
- 短期记忆（上下文窗口和循环耦合）：压缩在循环内，主流程上下文接近上限触发压缩，运行辅助流程，把全部历史消息+压缩提示词，先写 analysis 再写 summary，只取 summary 部分，插入边界信息
- 长期记忆（独立基础设施，完全解耦）：整合在循环外，后台辅助流程异步整合。核心记忆、记忆文件索引，不记代码或文本，提取工作由辅助流程根据索引去读
- 当项目到达一定规模或程度，整理记忆文件，上下文太长的时候自动进行压缩
- 需参考业界主流开源项目的源码核实设计是否符合上述要点

**Output Format:**
1. 现有上下文管理设计梳理报告
2. 业界参考实现对比分析
3. 短期记忆与长期记忆解耦设计方案
4. 优化实施计划与验证方式

### 9.4 注意力预算管理

<small style="color:#888">适用场景：超长任务的注意力管理，全局 Token 分配，确保关键信息在注意力范围内。</small>

**Role:** 注意力管理模块设计师

**Task:** 增强注意力预算管理器，实现全局 Token 分配，确保关键信息在注意力范围内。注意力预算管理器需实现多类预算分配与主动驱动压缩：当上下文接近上限时，由预算管理器主动触发压缩流程，而非被动等待。

**Constraints:**
- 确保关键信息（如当前任务上下文、核心配置、业务规则）始终在 LLM 注意力范围内
- 避免超长任务执行时注意力分散导致质量下降
- 预算管理器需主动驱动压缩，而非被动等待触发

**Output Format:**
1. 注意力预算分配策略（含多类预算定义）
2. 主动压缩触发机制说明
3. 关键信息保护清单
4. 模块接口与集成方案

### 9.5 一致性规则引擎

<small style="color:#888">适用场景：长任务一致性保障，扩展多种检测模式。</small>

**Role:** 一致性规则引擎设计师

**Task:** 增强一致性规则引擎，扩展多维度的一致性规则，覆盖多种检测场景。检测到不一致时通过事件上报主流程。

**Constraints:**
- 一致性规则需覆盖多维度，例如：数据一致性、逻辑一致性、时序一致性、规则一致性、状态一致性、关系一致性、配置一致性、命名一致性、风格一致性、约束一致性等
- 检测到不一致时通过事件上报主流程
- 规则设计需可扩展，便于后续新增检测维度

**Output Format:**
1. 一致性规则分类清单
2. 各规则的检测逻辑与触发条件
3. 事件上报机制设计
4. 规则扩展接口规范

### 9.6 双源可靠设计

<small style="color:#888">适用场景：数据可靠性设计，优先原版 Raw Sources，备用 SQLite 冷备份。</small>

**Role:** 数据存储架构师

**Task:** 设计记忆系统的双源可靠存储方案：主路径采用纯文本文件（Markdown），备用路径采用 SQLite 冷备份。

**Constraints:**
- 主路径：纯文本文件（Markdown），人类可读、LLM 易读、零依赖
- 原始素材层存放不可修改的原始资料，保证溯源性；结构化知识层由 LLM 维护
- 备用路径：SQLite 只做保险冷备份，当文件系统不可用时降级使用
- 设计原则：主路径纯文本文件优先，保证人类可读、LLM 易读、零依赖；SQLite 只做保险，不作为主路径

**Output Format:**
1. 双源存储架构图与数据流说明
2. 主路径设计与文件组织规范
3. 备用路径降级策略与触发条件
4. 数据同步与一致性保障机制

### 9.7 记忆系统持续优化

<small style="color:#888">适用场景：记忆系统的迭代优化，持续循环修复直到无 bug 与待优化项。</small>

**Role:** 记忆系统优化工程师

**Task:** 持续循环优化与修复记忆系统，直至无 bug 与待优化项。全面完成记忆系统的优化与完善，并依据项目代码同步更新记忆系统深度设计分析文档。

**Constraints:**
- 采用迭代式循环优化，每轮需明确待修复项与待优化项
- 当轮次未发现新问题时，方可结束循环
- 优化过程中需同步更新设计分析文档，保持文档与代码一致
- 每轮需输出本轮修复清单与验证结果

**Output Format:**

每轮迭代输出：
1. 本轮发现的问题与待优化项清单
2. 修复方案与实施记录
3. 验证结果（含回归测试）
4. 是否进入下一轮的判断与依据

最终输出：更新后的记忆系统深度设计分析文档

### 9.8 知识层合并重构

<small style="color:#888">适用场景：模块合并与架构简化，将旧检索层重构为 LLM Wiki 的原始素材层。</small>

**Role:** 架构重构工程师

**Task:** 对记忆系统进行重构优化：将旧检索层（Legacy — 纯检索层）与 LLM Wiki 整合，把旧检索层重构为 LLM Wiki 的原始素材层（Raw Sources）。统一接口，使记忆系统结构更清晰、符合软件工程设计规范。

**Constraints:**
- 消除冗余模块，统一接口设计
- 旧检索层重构为 LLM Wiki 的原始素材层，保留溯源性
- 重构后结构需符合软件工程设计规范
- 重构过程需保证已有功能不受影响

**Output Format:**
1. 现状分析与冗余模块清单
2. 重构方案与模块映射关系
3. 统一接口设计文档
4. 重构前后对比与验证报告

### 9.9 多任务隔离

<small style="color:#888">适用场景：多任务隔离设计，不同任务的记忆与知识系统模块互不影响。</small>

**Role:** 多任务隔离架构师

**Task:** 检查并优化多任务隔离能力实现，确保记忆与知识系统各模块按任务隔离。

**Constraints:**
- 不同任务之间，记忆与知识系统的各个模块需根据任务进行隔离，互不影响
- A 任务的数据不能污染 B 任务
- 多个任务可以并行执行，各自的记忆系统独立运作
- 支持按 taskId 隔离的存储路径设计

**Output Format:**
1. 多任务隔离架构设计图
2. 按 taskId 隔离的存储路径规范
3. 任务间数据隔离验证方案
4. 并行执行保障机制说明
