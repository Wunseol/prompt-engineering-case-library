## 一、部署运维与 DevOps

### 11.1 部署配置（Docker 容器化）

<small style="color:#888">适用场景：项目容器化部署，编写 Dockerfile 与 docker-compose 配置。</small>

**请为以下项目编写容器化部署配置：[项目类型：前端/后端/全栈]，[技术栈：如 Node.js + Express + PostgreSQL]，[部署目标：Docker / 云服务 / VPS]。**

**配置要求：**

**1. Dockerfile（多阶段构建优化镜像大小：构建阶段使用完整镜像编译，运行阶段使用 alpine/distroless 基础镜像；合理利用构建缓存；非 root 用户运行；添加 HEALTHCHECK 指令）；**

**2. docker-compose.yml（包含所有依赖服务：应用、数据库、缓存、消息队列；配置环境变量管理；配置数据卷持久化；配置网络隔离；配置资源限制 CPU/内存）；**

**3. 环境变量管理（区分开发/测试/生产环境；敏感信息使用 secrets；提供 .env.example 模板）；**

**4. 健康检查（HTTP 健康检查端点 /health；readiness 与 liveness 区分；检查间隔与超时设置）；**

**5. 日志收集（输出到 stdout/stderr；结构化 JSON 日志；日志级别控制）；**

**6. 反向代理（Nginx 配置：负载均衡、SSL 终止、静态资源缓存、Gzip 压缩）。**

**约束：**

- **镜像大小必须小于 500MB；**
- **禁止在镜像中硬编码密钥；**
- **必须使用多阶段构建；**
- **健康检查端点不得暴露敏感信息；**
- **日志必须输出到 stdout 便于日志聚合。**

**输出格式：**

## 1. Dockerfile
## 2. docker-compose.yml
## 3. 环境变量模板
## 4. 健康检查端点
## 5. Nginx 配置
## 6. 部署文档

### 11.2 CI/CD 流水线

<small style="color:#888">适用场景：搭建自动化构建、测试、部署流水线。</small>

**请为以下项目设计完整的 CI/CD 流水线：[项目：项目名]，[仓库：GitHub/GitLab/Gitee]，[技术栈：列出]，[部署环境：开发/测试/生产]。**

**流水线设计：**

**1. 流程设计（代码检查 → 构建 → 单元测试 → 集成测试 → 安全扫描 → 构建镜像 → 部署到对应环境 → 冒烟测试 → 通知）；**

**2. 阶段配置（每阶段定义：触发条件、执行命令、超时时间、失败策略、产物上传）；**

**3. 分支策略（main 分支触发生产部署、develop 分支触发测试环境部署、feature 分支触发开发环境部署、PR 触发代码检查）；**

**4. 配置文件（编写 [GitHub Actions/GitLab CI/Jenkins] 配置文件，包含完整的 YAML/JSON 配置）；**

**5. 质量门禁（代码覆盖率阈值、Lint 错误数限制、安全漏洞扫描、镜像大小限制）；**

**6. 通知机制（构建失败通知、部署成功通知、Slack/钉钉/邮件集成）；**

**7. 回滚机制（版本管理、回滚脚本、数据库迁移回滚）。**

**约束：**

- **每阶段必须有明确的时间预算；**
- **质量门禁不通过必须阻断流水线；**
- **部署前必须通过所有自动化测试；**
- **生产部署必须支持灰度或金丝雀发布；**
- **回滚必须在 5 分钟内完成。**

**输出格式：**

## 1. 流程设计
## 2. 阶段配置
## 3. 分支策略
## 4. 配置文件
## 5. 质量门禁
## 6. 通知机制
## 7. 回滚机制

### 11.3 Kubernetes 部署

<small style="color:#888">适用场景：将应用部署到 Kubernetes 集群。</small>

**请为以下应用设计 Kubernetes 部署方案：[应用描述：类型、技术栈、依赖服务、预估 QPS]。**

**部署方案：**

**1. 资源规划（CPU/内存 Request 与 Limit、副本数、HPA 自动扩缩容配置）；**

**2. 工作负载（Deployment 配置：镜像、环境变量、健康检查、就绪探针、存活探针、启动探针、优雅终止）；**

**3. 服务暴露（Service 类型：ClusterIP/NodePort/LoadBalancer；端口映射；会话保持）；**

**4. 入口路由（Ingress 配置：域名、TLS、路径路由、限流、重写）；**

**5. 配置管理（ConfigMap：非敏感配置；Secret：敏感信息；热更新策略）；**

**6. 持久化（PersistentVolume/PersistentVolumeClaim：数据卷、存储类、备份策略）；**

**7. 网络策略（NetworkPolicy：入向/出向流量限制、命名空间隔离）；**

**8. 弹性能力（PodDisruptionBudget：维护期间最小可用副本；HPA：基于 CPU/内存/自定义指标扩缩容；CronJob：定时任务）。**

**约束：**

- **资源 Request/Limit 必须基于压测数据；**
- **健康检查必须区分 liveness 和 readiness；**
- **Secret 不得提交到代码仓库，使用外部密钥管理；**
- **生产环境必须配置 PDB；**
- **HPA 扩缩容必须设置稳定窗口避免抖动。**

**输出格式：**

## 1. 资源规划
## 2. Deployment
## 3. Service
## 4. Ingress
## 5. ConfigMap/Secret
## 6. 持久化
## 7. NetworkPolicy
## 8. 弹性能力

### 11.4 可观测性体系

<small style="color:#888">适用场景：构建完整的日志、指标、追踪可观测性体系。</small>

**请为以下系统设计完整的可观测性体系：[系统描述：技术栈、微服务数量、部署环境]。**

**设计维度：**

**1. 日志体系（日志规范：时间戳、级别、TraceID、SpanID、服务名、消息；日志收集：Filebeat/Fluentd 采集；日志存储：Elasticsearch/Loki；日志查询：Kibana/Grafana；日志保留策略：热/温/冷分层）；**

**2. 指标体系（业务指标：QPS、错误率、延迟分位、转化率；系统指标：CPU、内存、磁盘、网络、GC；自定义指标：Prometheus Client；指标采集：Prometheus + ServiceMonitor；指标展示：Grafana Dashboard；告警规则：基于阈值与异常检测）；**

**3. 链路追踪（追踪接入：OpenTelemetry SDK；追踪存储：Jaeger/Tempo；采样策略：头部采样或尾部采样；跨度设计：关键节点 Span；上下文传播：W3C Trace Context）；**

**4. 告警体系（告警分级：P0/P1/P2/P3；告警路由：按服务/严重度路由；告警通知：Slack/钉钉/邮件/电话；告警抑制：同类告警抑制、维护窗口；告警闭环：认领→处理→复盘）；**

**5. 监控大盘（系统总览大盘、服务详情大盘、业务指标大盘、告警大盘）。**

**约束：**

- **日志必须结构化（JSON 格式）；**
- **指标必须遵循 USE/RED 方法论；**
- **链路追踪必须覆盖所有跨服务调用；**
- **告警必须有明确的处理流程和 SLA；**
- **监控大盘必须分层次（高管/研发/运维）。**

**输出格式：**

## 1. 日志体系
## 2. 指标体系
## 3. 链路追踪
## 4. 告警体系
## 5. 监控大盘

### 11.5 生产环境运维

<small style="color:#888">适用场景：生产环境的日常运维、健康检查、扩缩容、回滚、灾备。</small>

**请为以下生产系统设计运维手册：[系统描述：架构、部署方式、SLA 要求]。**

**运维手册内容：**

**1. 日常巡检（每日检查项：服务健康、资源水位、慢查询、错误率、证书有效期；每周检查项：容量趋势、备份验证、依赖更新；每月检查项：架构评审、故障演练、容量规划）；**

**2. 扩缩容操作（垂直扩容：调整资源 Limit；水平扩容：调整副本数或 HPA 阈值；数据库扩容：分库分表、读写分离；缓存扩容：分片、集群模式；扩容前检查项与回滚方案）；**

**3. 回滚操作（应用回滚：版本切换、镜像回退；数据库回滚：迁移脚本回退、数据备份恢复；配置回滚：ConfigMap/Secret 版本回退；回滚验证与影响评估）；**

**4. 灾备方案（RTO/RPO 目标；同城双活/异地多活架构；数据同步方案；故障切换流程；灾备演练计划）；**

**5. 应急预案（常见故障预案：数据库宕机、缓存雪崩、消息队列堆积、依赖服务不可用；应急联系人；通讯录；决策树）。**

**约束：**

- **所有操作必须有详细的操作步骤和验证方法；**
- **扩缩容必须有容量评估和回滚方案；**
- **回滚操作必须包含数据一致性检查；**
- **灾备方案必须定期演练验证；**
- **应急预案必须有明确的升级路径。**

**输出格式：**

## 1. 日常巡检
## 2. 扩缩容操作
## 3. 回滚操作
## 4. 灾备方案
## 5. 应急预案

### 11.6 蓝绿部署与灰度发布

<small style="color:#888">适用场景：零停机部署与渐进式发布。</small>

**请为以下系统设计零停机部署与灰度发布方案：[系统描述：服务类型、依赖、用户量]。**

**设计方案：**

**1. 蓝绿部署（蓝色环境当前版本、绿色环境新版本；切换策略：DNS 切换/负载均衡权重/Service Selector；切换前验证：健康检查、冒烟测试、数据一致性检查；切换后观察：监控指标、错误率、用户反馈；回滚方案：快速切回蓝色环境）；**

**2. 金丝雀发布（流量切分策略：基于 Header/Cookie/百分比；金丝雀节点部署：1 个节点先承接 1% 流量；观察指标：错误率、延迟、业务指标；逐步扩大：1% → 10% → 50% → 100%；自动回滚机制：错误率超阈值自动切回）；**

**3. A/B 测试（实验设计：实验组/对照组分组规则；指标设计：核心指标/辅助指标/护栏指标；统计显著性：样本量、置信度、最小可检测效应；实验时长：基于日活与转化周期）；**

**4. 特性开关（开关粒度：功能级/模块级/用户级；开关管理：配置中心/数据库/环境变量；开关生命周期：实验→全量→固化；开关监控：使用率、错误率关联）。**

**约束：**

- **蓝绿部署必须保证数据库 Schema 兼容；**
- **金丝雀发布必须设置自动回滚阈值；**
- **A/B 测试必须有统计显著性验证；**
- **特性开关必须有生命周期管理，避免开关膨胀。**

**输出格式：**

## 1. 蓝绿部署
## 2. 金丝雀发布
## 3. A/B 测试
## 4. 特性开关
## 5. 监控与回滚
