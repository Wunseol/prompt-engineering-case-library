## 一、代码生成与实现

### 6.1 从 Spec 到代码的实现流程

<small style="color:#888">适用场景：将 Spec 文档转化为可执行代码的标准化流程。</small>

**Role:** 高级开发工程师，负责基于 Spec 文档进行端到端的代码实现。

**Task:** 基于以下 Spec 文档实现代码：{Spec 文档路径或内容}

实现流程：
1. Spec 解析（提取 Mission、Tech Stack、Requirements、Scenarios、Verification 关键信息）
2. 任务拆解（按 Requirements 拆解为可独立实现的技术任务，每个任务标注依赖关系）
3. 实现顺序（按依赖关系排序：基础设施 → 数据层 → 业务层 → 接口层 → 表现层）
4. 分步骤实现（每次只实现一个任务，输出完整可运行代码）
5. 单元测试（为每个任务编写对应的单元测试）
6. 集成验证（按 Scenarios 验证业务流程）
7. 文档同步（更新 README 和 API 文档）

**Constraints:**
- 每个任务的代码必须可直接运行，不得包含 TODO 或占位符
- 每次实现必须包含对应的测试用例
- 代码必须符合 Tech Stack 指定的技术栈版本
- 不得引入未在 Spec 中声明的依赖

**Output Format:**
## 1. Spec 解析
## 2. 任务拆解
## 3. 实现顺序
## 4. 分步骤实现
## 5. 单元测试
## 6. 集成验证
## 7. 文档同步

### 6.2 代码生成最佳实践

<small style="color:#888">适用场景：指导 AI 生成高质量、可维护、安全的代码。</small>

**Role:** 高级全栈开发工程师，遵循语言/框架官方最佳实践进行代码实现。

**Task:** 按以下最佳实践生成代码：{功能描述}

生成规范：
1. 上下文优先（生成前先阅读相关文件理解现有代码风格、命名规范、架构模式）
2. 单一职责（每个函数/类只做一件事，函数行数不超过 50 行，类的方法数不超过 20 个）
3. 防御式编程（输入验证、空值检查、边界条件处理、异常捕获）
4. 安全编码（不硬编码密钥、参数化查询、输出转义、最小权限原则）
5. 可测试性（依赖注入、接口抽象、避免全局状态、纯函数优先）
6. 性能意识（避免 N+1 查询、减少不必要的对象创建、合理使用缓存、异步处理 IO 密集操作）
7. 可读性（有意义的命名、必要的注释、复杂逻辑必须有解释）

**Constraints:**
- 代码必须符合语言/框架的官方最佳实践
- 不得使用已弃用的 API
- 异常处理必须区分可恢复错误和不可恢复错误
- 所有公共 API 必须有文档注释

**Output Format:**
## 1. 实现代码
## 2. 单元测试
## 3. 使用示例
## 4. 注意事项

### 6.3 API 集成架构

<small style="color:#888">适用场景：设计或评估与外部系统/第三方服务的 API 集成方案。</small>

**Role:** 集成架构师，负责外部 API 集成的架构设计与代码骨架实现。

**Task:** 为以下外部 API 设计完整的集成架构：{API 名称及用途描述}

设计维度：
一、集成模式选择（对比同步请求-响应、异步消息队列、Webhook 回调、事件驱动、批量同步，输出模式 | 适用场景 | 优势 | 劣势 | 推荐度表格，最终推荐必须基于具体场景论证）
二、认证与授权（认证类型：API Key / OAuth 2.0 / JWT / HMAC / mTLS，Token 生命周期管理、刷新策略、权限最小化原则）
三、重试与退避策略（重试条件：网络错误/超时/5xx/429/业务错误，最大重试次数、退避算法：固定/指数/指数+抖动、退避参数、重试上下文传递、死信队列处理）
四、幂等性保障（幂等键设计、幂等窗口期、幂等存储选择、重复请求处理策略）
五、数据一致性（最终一致性方案、补偿机制、对账策略、数据冲突解决）
六、可观测性（关键指标：调用延迟/错误率/限流率/队列深度，日志规范：请求ID/响应码/耗时/重试次数，分布式追踪集成，告警规则与阈值）
七、安全防护（传输加密、请求签名、敏感字段脱敏、速率限制、IP 白名单、证书轮换策略）
八、集成代码骨架（客户端封装类、重试中间件、幂等中间件、日志中间件、健康检查端点，使用 {指定语言/框架}）

**Constraints:**
- 模式选择必须基于业务场景
- 重试策略必须区分可重试错误和不可重试错误
- 幂等方案必须覆盖并发重复请求
- 所有超时参数必须给出具体值和计算依据
- 代码骨架必须可直接运行

**Output Format:**
## 1. 集成模式选择
## 2. 认证与授权
## 3. 重试与退避策略
## 4. 幂等性保障
## 5. 数据一致性
## 6. 可观测性
## 7. 安全防护
## 8. 集成代码骨架

### 6.4 性能优化

<small style="color:#888">适用场景：系统化定位性能瓶颈并制定优化方案。</small>

**Role:** 性能工程专家，负责系统化定位性能瓶颈并制定优化方案。

**Task:** 针对以下性能问题进行系统化优化：{描述性能问题现象，包括系统类型、技术栈、问题表现、当前指标}

优化流程：
第一步 建立基线（要求提供或定义：P50/P95/P99 延迟、吞吐量、资源利用率 CPU/内存/磁盘/网络、错误率；如果无数据，告知应采集什么指标、采集时长、采集工具）
第二步 瓶颈分析（按优先级排查：1.计算瓶颈 CPU 密集/算法复杂度 2.内存瓶颈 GC 压力/内存泄漏/大对象分配 3.IO 瓶颈 磁盘/网络/数据库 4.锁与并发瓶颈 锁竞争/线程池耗尽 5.外部依赖瓶颈 第三方 API/缓存未命中；每个瓶颈输出：瓶颈描述 | 证据 | 影响程度）
第三步 影响排序（按"影响度 × 修复成本"排序，输出表格：瓶颈 | 影响度 1-5 | 修复成本 1-5 | 优先级得分 | 排序位次）
第四步 优化方案（对每个高优先级瓶颈给出：方案描述 | 预期收益量化 | 实施步骤 | 回归风险 | 验证方法，必须包含代码示例或配置变更）
第五步 验证计划（目标 P50/P95/P99 延迟、目标吞吐量、压测方案、回归测试范围、监控告警阈值）

**Constraints:**
- 禁止在无基线数据时给优化建议
- 瓶颈分析必须数据驱动
- 优化方案必须量化预期收益
- 每个方案必须说明回归风险和回滚策略
- 禁止"加机器"作为首选方案

**Output Format:**
## 1. 基线指标
## 2. 瓶颈分析
## 3. 影响排序
## 4. 优化方案
## 5. 验证计划

### 6.5 代码规范与风格统一

<small style="color:#888">适用场景：为项目制定统一的代码规范，确保团队代码风格一致。</small>

**请为以下项目制定完整的代码规范：[项目描述，包括技术栈、团队规模、协作模式]。规范维度：1. 命名规范（变量、函数、类、文件、常量、枚举的命名规则，区分大小写约定）；2. 格式规范（缩进、空格、换行、括号位置、行长度限制）；3. 注释规范（文件头注释、函数注释、类注释、复杂逻辑注释、TODO 注释格式）；4. 文件组织（目录结构、文件命名、模块划分、入口文件规范）；5. 错误处理规范（异常分类、错误码体系、错误信息格式、日志规范）；6. 测试规范（测试文件命名、测试用例组织、Mock 规范、覆盖率要求）；7. 依赖管理（依赖版本锁定、依赖审计、禁止依赖清单）。输出格式：可直接配置到 ESLint/Prettier/Checkstyle 等工具的配置文件 + 规范文档。约束：规范必须与项目技术栈兼容；必须提供工具配置文件示例；覆盖率要求必须分阶段给出（MVP/成长期/成熟期）；禁止依赖清单必须说明理由。输出格式：## 1. 命名规范 ## 2. 格式规范 ## 3. 注释规范 ## 4. 文件组织 ## 5. 错误处理规范 ## 6. 测试规范 ## 7. 依赖管理 ## 8. 工具配置**

### 6.6 增量开发与版本控制

<small style="color:#888">适用场景：指导 AI 进行增量式开发，配合版本控制管理变更。</small>

**请按增量开发模式实现以下功能：[功能描述]。增量开发规范：1. 分支策略（每个功能从 main 分支拉取 feature 分支，命名规范：feature/[功能名]-[日期]）；2. 提交规范（每个独立逻辑变更一个提交，提交信息格式：type: subject，type 包括 feat/fix/refactor/test/docs/chore）；3. 增量交付（每个增量必须可独立运行和验证，增量大小控制在 200 行代码以内）；4. 代码审查点（每个增量完成后自检：编译通过、测试通过、无 Lint 错误、无安全漏洞）；5. 合并策略（功能完成后发起 PR，至少 1 人审查通过后合并，合并前必须 rebase 到最新 main）；6. 版本 tagging（按语义化版本规范：MAJOR.MINOR.PATCH，标注 pre-release 时使用 alpha/beta/rc）。约束：每次提交必须包含完整的测试用例；增量交付必须可回滚；合并前必须通过 CI 流水线；版本号变更必须遵循语义化版本规范。输出格式：## 1. 分支策略 ## 2. 提交规范 ## 3. 增量交付计划 ## 4. 代码审查检查清单 ## 5. 合并流程 ## 6. 版本管理**

### 6.7 代码生成后的自检清单

<small style="color:#888">适用场景：AI 生成代码后进行系统化自检，确保代码质量。</small>

**请对刚才生成的代码进行系统化自检，按以下清单逐项验证：1. 功能正确性（☐ 实现了 Spec 中所有要求的功能 ☐ 边界条件已处理 ☐ 异常路径已覆盖 ☐ 业务规则已实现）；2. 代码质量（☐ 无重复代码 ☐ 函数职责单一 ☐ 命名有意义 ☐ 无魔法数字 ☐ 无过深嵌套）；3. 安全性（☐ 无硬编码密钥 ☐ 输入已验证 ☐ 输出已转义 ☐ 权限已校验 ☐ 敏感数据已脱敏）；4. 性能（☐ 无 N+1 查询 ☐ 无不必要的同步操作 ☐ 无大对象频繁拷贝 ☐ 缓存使用合理）；5. 可维护性（☐ 有必要注释 ☐ 复杂逻辑有解释 ☐ 公共 API 有文档 ☐ 遵循项目代码风格）；6. 可测试性（☐ 依赖可注入 ☐ 无全局状态 ☐ 纯函数优先 ☐ 已编写单元测试）；7. 兼容性（☐ 符合目标运行时版本 ☐ 无弃用 API ☐ 跨平台兼容）；8. 错误处理（☐ 异常分类合理 ☐ 错误信息友好 ☐ 有回滚机制 ☐ 有降级方案）。对每项检查输出：检查项 | 结果（通过/未通过）| 问题描述 | 修复方案。约束：自检必须逐项进行，不得跳过；未通过项必须给出修复方案和修复后的代码；最终输出修复后的完整代码。输出格式：## 1. 功能正确性 ## 2. 代码质量 ## 3. 安全性 ## 4. 性能 ## 5. 可维护性 ## 6. 可测试性 ## 7. 兼容性 ## 8. 错误处理 ## 9. 修复后代码**

### 6.8 多语言/多框架适配

<small style="color:#888">适用场景：将同一份 Spec 适配到不同编程语言或框架实现。</small>

**请将以下 Spec 适配到 [目标语言/框架] 实现：[Spec 文档路径或内容]。适配维度：1. 语言特性映射（原 Spec 中的设计模式在目标语言中的惯用写法，如 Java 的 Stream vs Python 的列表推导）；2. 框架对应关系（原框架的组件在目标框架中的对应实现，如 Spring Boot 的 @RestController vs Express 的 router）；3. 依赖库替换（原依赖在目标生态中的等价库，对比功能、性能、维护活跃度）；4. 测试框架替换（JUnit vs pytest vs Jest，测试用例格式转换）；5. 构建工具替换（Maven/Gradle vs npm/pip/cargo，构建配置迁移）；6. 部署方式适配（容器化、云函数、PaaS 部署的差异处理）。每个维度输出：原实现 | 目标实现 | 差异说明 | 迁移注意事项。约束：适配必须基于目标语言/框架的最佳实践，不得生硬翻译；依赖库替换必须评估 License 兼容性；测试用例必须保持语义等价；构建配置必须可在目标环境直接运行。输出格式：## 1. 语言特性映射 ## 2. 框架对应关系 ## 3. 依赖库替换 ## 4. 测试框架替换 ## 5. 构建工具替换 ## 6. 部署方式适配**
