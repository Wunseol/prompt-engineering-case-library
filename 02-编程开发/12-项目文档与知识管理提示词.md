## 一、项目理解与文档建设

### 12.1 项目结构阅读与理解

<small style="color:#888">适用场景：新接手项目的开发者建立对项目的整体认知，不修改任何文件，仅通过提问方式了解项目。</small>

**Role:** 新接手项目的开发者，需要建立对项目的整体认知。

**Task:** 详细阅读{项目名称}的项目文档，了解该项目的项目结构；完成了解后等待后续指令，当前工作仅为后续的优化工作做准备；了解项目后，通过一系列问题进一步深入理解项目。

**Constraints:**
- 不修改任何文件
- 本任务为提问式了解任务
- 仅通过提问方式了解项目，不进行任何写入操作

**Output Format:**
提问式清单与对项目结构的理解摘要，等待后续指令。

---

### 12.2 项目文档体系建设

<small style="color:#888">适用场景：为现有项目补充并重构文档，让团队新成员能根据文档深度理解项目，文档与源码深度结合并补充软件工程图。</small>

**Role:** 项目文档架构师。

**Task:** 整理优化项目文档，拆解检查研究项目结构，统合项目需求文档、实施文档、项目报告等，让读者彻底读懂项目代码，并让团队新成员能根据这些项目报告深度了解项目；运用软件工程思维重构项目文档，补充所有软件工程所需的图（用 Mermaid 语法画图）。

**Constraints:**
- 文档需与当前项目源码深度结合，讲解代码和对应的跳转路径能真正跳转到对应源码（链接适配 GitHub、VSCode 等）
- 文档开头应有文档导航栏，设计合理的学习路线
- 整理并排序文档序号，让新人了解并具备参与项目的能力
- Mermaid 图要详细，符合当前的项目结构，与项目源码深度结合
- 同步更新 README 文件
- 所有文档放到项目文档文件夹中，方便开发者了解和参与开发

**Output Format:**
重构后的项目文档集（含导航栏、学习路线、Mermaid 软件工程图），存放于项目文档文件夹中，并同步更新后的 README。

---

### 12.3 文档分类与归档

<small style="color:#888">适用场景：文档数量膨胀后的分类整理，按类型分文件夹归档并排序。</small>

**Role:** 文档管理员。

**Task:** 对项目文档进行分类整理，在项目文档下建立文件夹分类归档（如需求文档放到需求文档文件夹、逻辑审查放到逻辑审查文件夹）；整理主目录下的文档到对应的项目文档中。

**Constraints:**
- 按文档类型建立分类文件夹
- 分类文件夹也要排序
- 主目录文档归档到对应分类文件夹

**Output Format:**
分类归档后的项目文档目录结构。

---

### 12.4 README 优化与命名规范

<small style="color:#888">适用场景：项目初始化或规范化阶段，统一命名规范、补充必要文件，并优化 README 结构使部署说明前置。</small>

**Role:** 项目规范化工程师。

**Task:** 检查项目结构，优化项目命名和代码规范，并添加 README 和开源协议文件；根据项目文档优化 README 文件，将项目部署启动方式放在靠前位置，其他内容靠后排列。

**Constraints:**
- 项目部署启动方式必须放在 README 靠前位置
- 其他内容靠后排列
- 符合主流项目规范
- 添加 README 与开源协议文件

**Output Format:**
优化后的 README 文件与开源协议文件，以及统一的命名规范说明。

---

### 12.5 需求文档拆解

<small style="color:#888">适用场景：将模糊需求转化为结构化的需求文档，文档需与项目源码深度结合。</small>

**Role:** 需求分析师。

**Task:** 拆解检查研究项目结构，统合项目需求文档和实施文档，写成项目报告，让读者彻底读懂项目代码，让团队新成员能根据这些项目报告深度了解项目。

**Constraints:**
- 文档需与当前项目源码深度结合
- 讲解代码和对应的跳转路径能真正跳转到对应源码
- 让新人充分了解并具备参与项目的能力
- 文档放到项目文件夹中，方便开发者了解和参与开发

**Output Format:**
结构化的项目报告与需求文档，存放于项目文件夹中。

## 二、文档质量与一致性保障

### 12.6 文档正确性校验

<small style="color:#888">适用场景：文档与源码一致性校验，逐一对照项目源码，确保文档严谨性。</small>

**Role:** 文档质量审核员。

**Task:** 根据项目结构和项目源码同步项目文档，全面检查项目代码和项目文档是否真实对应，校对优化整理。

**Constraints:**
- 所有项目文档必须逐一对照项目源码
- 必须逐一对照校验，不得遗漏
- 项目文档的严谨性是核心要求

**Output Format:**
校对优化整理后的项目文档及一致性校验报告。

---

### 12.7 长上下文压缩

<small style="color:#888">适用场景：项目进行到中后期，规划文档和规格文档上下文过长时压缩精简，消除冗余只留关键信息。</small>

**Role:** 上下文压缩助手。

**Task:** 将工作目录中的规划文档和规格文档压缩为摘要。

**Constraints:**
- 消除冗余
- 只保留关键信息
- 冗余文件予以清理

**Output Format:**
精简后的摘要文档及被清理的冗余文件清单。

---

### 12.8 文档修改优先级规则

<small style="color:#888">适用场景：建立文档维护的规范化流程，确保修改顺序统一、可追溯。通用文档修改流程提示词。</small>

**Role:** 文档维护工程师。

**Task:** 按照规范化顺序对项目文档进行修改，确保修改顺序统一、可追溯。

**Constraints:**
- 修改必须严格按照以下顺序执行，不得跳跃：
  1. 先改技术栈清单
  2. 再改学习文档
  3. 再改案例文档（案例文档移到最后）
  4. 最后加上更新时间和维护者
- 每一步完成后再进入下一步
- 修改需可追溯

**Output Format:**
按顺序修改后的文档集合，包含技术栈清单、学习文档、案例文档（移至最后），并在末尾标注更新时间与维护者。

---

## 三、源码学习与逆向分析

### 12.9 学习开源项目源码

<small style="color:#888">适用场景：学习复杂开源项目源码，快速掌握其架构、结构与设计思想，强调拆解与能力转化，目标是能基于源码设计新项目或继续开发。</small>

**Role:** 源码学习导师。

**Task:** 分析拆解目标开源项目源码，从零开始讲解其设计、结构、开发思想等，让学习者充分了解并具备基于该源码设计其他项目或继续开发的能力；解析要透彻清晰；将学习需求拆解为详细的需求文档。

**Constraints:**
- 解析要透彻清晰
- 需求文档需分各模块拆解
- 若需求较庞大，可写多个 md 文件
- 文件名自定义
- 输出 md 文件统一放在 `docs/` 目录下

**Variables:**
- `{项目名称}`：待学习的开源项目名称（必填）

**Output Format:**
分模块的详细需求文档（md 文件），输出至 `docs/` 目录下，文件名由 AI 自定。

---

### 12.10 专项技术深入学习

<small style="color:#888">适用场景：针对特定技术进行深度学习和文档化，强调结构、二次开发等深入了解。</small>

**Role:** 技术学习文档撰写专家。

**Task:** 针对目标技术撰写详细的学习文档，不仅要讲解使用方法，还要讲解项目结构、如何二次开发等深入了解内容。

**Constraints:**
- 具体参照官方技术文档
- 学习前后顺序、时效性、严谨性非常重要
- 检查开源项目最近的更新维护情况
- 按官方推荐撰写，可能随时间变化的技术需标注
- 内容需覆盖：使用方法、项目结构、二次开发

**Variables:**
- `{技术名}`：待深入学习的技术名称（必填）

**Output Format:**
结构化的专项技术学习文档，包含使用方法、项目结构、二次开发等章节。

---

### 12.11 项目结构理解

<small style="color:#888">适用场景：接手或优化项目前快速了解整体结构，作为后续开发的前置步骤。</small>

**Role:** 项目分析师。

**Task:** 详细阅读{项目名称}文档，深入了解项目结构，为下一步优化做准备。

**Constraints:**
- 仅理解结构，不进行修改
- 作为后续优化的前置步骤

**Variables:**
- `{项目名称}`：待理解的项目名称（必填）

**Output Format:**
项目结构理解摘要，等待后续优化指令。

<small style="color:#888">使用建议：可结合其他提示词使用，先用本提示词了解结构，再用优化提示词改进。</small>

## 四、技术栈与知识体系管理

### 12.12 构建技术栈清单

<small style="color:#888">适用场景：初创团队或新部门搭建技术体系时使用，构建科技树与各方向学习大纲。</small>

**Role:** 技术体系架构师。

**Task:** 根据团队或公司情况构建科技树，按不同技术方向确定对应技术清单，生成各方向的技术栈清单和学习大纲文档。

**Constraints:**
- 每个方向的学习大纲专注于要学习的技术
- 不仅罗列技术栈，还需有详细的学习路径（从入门到精通）
- 整理大纲内容，不写能力等级体系和学习路径总览
- 不分阶段，直接队列排列，后续以技术栈名称作为标题
- 删除多余空行，学习资源只放官方链接，不要纸质书籍
- 相似技术栈用高一级标题合并
- 技术方向由 AI 自行确定

**Variables:**
- `{公司类型描述}`：公司或团队类型描述（必填）
- `{业务描述}`：业务范围描述（必填）

**Output Format:**
按技术方向划分的科技树、各方向技术栈清单与学习大纲文档。

---

### 12.13 技术栈持续优化

<small style="color:#888">适用场景：定期更新和优化团队技术栈清单，保持时效性，并联动生成对应学习文档。</small>

**Role:** 技术栈维护工程师。

**Task:** 优化并完善各个方向的技术栈清单，重点关注开源项目、软件、框架、技术；每个方向增加主流的开源项目技术框架，然后以各方向技术栈清单为基准，在各方向文件夹下撰写具体的学习文档。

**Constraints:**
- 内容要具体参照官方技术文档
- 学习前后顺序、时效性、严谨性等都非常重要
- 检查开源项目最近的更新维护情况
- 按官方推荐撰写，可能随时间变化的技术需标注
- 重点关注开源项目、软件、框架、技术

**Output Format:**
更新后的各方向技术栈清单，以及在各方向文件夹下生成的学习文档。

---

### 12.14 学习文档深度优化

<small style="color:#888">适用场景：定期审视和优化学习文档质量，从五个关键维度系统性提升。</small>

**Role:** 学习文档质量审核员。

**Task:** 对指定方向的学习文档进行全面检查与优化，从五个关键维度系统性提升文档质量，处理完成后提供详细的优化报告。

**Constraints:**
- 内容时效性：检查开源项目最近的更新维护情况，将最新动态整合到文档中
- 信息严谨性：严格按官方推荐的规范和最佳实践撰写内容，对可能随时间变化的技术、函数、库等进行系统性核查，确认其当前有效性，对存在版本差异或使用限制的内容进行明确标注
- 逻辑顺序：优化组织结构和内容呈现顺序，确保知识体系连贯
- 内容准确性：全面核对技术描述、代码示例和配置说明
- 版本兼容性：明确标注功能差异和兼容性要求

**Variables:**
- `{指定方向}`：待优化的学习文档所属技术方向（必填）

**Output Format:**
优化后的学习文档，以及详细的优化报告（覆盖五个维度的检查与改动记录）。

## 五、项目复盘与迭代

### 12.15 开发复盘

<small style="color:#888">适用场景：项目阶段性完成后进行复盘总结，提炼经验教训并规划后续工作。</small>

**Role:** 项目复盘师。

**Task:** 复盘本次开发工作，总结经验与教训，明确开发过程中的优先顺序，总结本次开发工作进度，并给出后续开发计划。

**Constraints:**
- 明确开发过程中的优先顺序
- 总结经验与教训
- 总结本次开发工作进度
- 给出后续开发计划

**Output Format:**
复盘报告，包含经验教训、优先顺序、进度总结、后续开发计划。

---

### 12.16 持续优化

<small style="color:#888">适用场景：迭代式持续优化，发现新的改进点并关注主流开源项目动态。</small>

**Role:** 持续优化工程师。

**Task:** 根据之前的优化提示，继续检查还有哪些可以优化的方向；继续寻找优化方向，关注主流开源项目动态。

**Constraints:**
- 关注主流开源项目
- 近期 star 数飙升的项目多关注
- 基于已有优化提示延伸寻找新改进点

**Output Format:**
新的优化方向建议清单，附关注的主流开源项目动态说明。
