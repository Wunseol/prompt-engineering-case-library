## 一、5分钟了解项目

### 项目是什么？

一个**纯 Markdown 知识库**，整理了提示词工程从入门到精通的完整知识体系。

### 解决什么问题？

- **信息分散**：提示词知识散落在论文、博客、GitHub 中，本项目集中整理
- **不可即用**：很多教程只讲原理不给模板，本项目每项技术都有可复制模板
- **缺乏量化**：不知道哪种技术好，本项目提供论文级效果数据
- **英文门槛**：大量优质内容是英文，本项目提供中文版

### 不是什么？

- 不是一个代码项目（"源码"即 Markdown 文件）
- 不是一个 AI 工具（不调用任何 API）
- 不是一个论文翻译项目（整合而非逐字翻译）

## 三、15分钟深度理解核心文件

### 3.1 核心技术手册的结构逻辑

```
17种技术按以下逻辑排列：

基础提示（不需要示例）         推理增强（让AI会思考）
  零样本 → 少样本               CoT → ToT → Self-Consistency
                                   ↓
输出控制（让AI听指挥）         行动能力（让AI会做事）
  结构化输出 → 否定约束          ReAct → 系统提示
  宪法AI → 角色提示
                                   ↓
迭代优化（让AI越做越好）       多步编排（让AI做复杂事）
  迭代优化 → 自我审查            提示链 → 任务分解
  元提示 → Chain of Draft
```

**核心技术速查**（来自 [01-开源项目与资源索引.md](../10-开源生态/01-开源项目与资源索引.md) 第七节）：

| 你要做什么 | 用什么技术 | 在哪个章节 |
|-----------|-----------|-----------|
| 简单分类/摘要 | 零样本提示 | 核心技术手册 一 |
| 需要特定输出格式 | 少样本提示 | 核心技术手册 二 |
| 数学/逻辑推理 | CoT + Self-Consistency | 核心技术手册 三+五 |
| 复杂规划/多方案 | ToT | 核心技术手册 四 |
| 调用工具/API | ReAct | 核心技术手册 六 |
| 精确格式输出 | 结构化输出 | 核心技术手册 十一 |
| 安全关键场景 | 宪法AI + 自我审查 | 核心技术手册 十+十六 |
| 降低Token成本 | Chain of Draft | 核心技术手册 十三 |

### 3.2 模板四字段模式

所有模板文件都遵循"四字段"结构（来自 [02-核心技术手册.md](../01-入门与理论/02-提示词工程核心技术手册.md) 附录二）：

```
Role（角色）        → 你是谁
Task（任务）        → 你要做什么
Constraints（约束） → 你不能做什么 / 限制条件
Output Format（输出格式） → 结果长什么样
```

**实际例子**（来自 [01-日常写作与办公提示词模板.md](../04-AI办公写作/01-日常写作与办公提示词模板.md)）：

```
你是一位高效的团队协作者...     ← Role
根据以下工作记录，生成周报       ← Task
只包含核心任务 / 300字以内 / 语气专业  ← Constraints
## 本周进展 / ## 下周计划        ← Output Format
```

### 3.3 系统提示词案例

[02-AI编程助手系统提示词案例.md](../02-编程开发/02-AI编程助手系统提示词案例.md) 是项目的"深度"所在：

- **逆向工程**：分析 Cursor/Windsurf/Claude Code/Devin 的"灵魂"（系统提示词）
- **通用架构**：提炼出7层通用架构（身份→行为→工具→代码→安全→错误→输出）
- **可即用模板**：3个可直接复制使用的编程助手模板

**学习路径**：先理解7层架构 → 再看4个工具的具体实现 → 最后用通用模板设计自己的

## 四、如何参与贡献

### 4.1 贡献类型

| 类型 | 示例 | 难度 |
|------|------|------|
| **修错别字** | 修正拼写、格式错误 | ⭐ |
| **补充示例** | 给现有模板添加填充示例 | ⭐⭐ |
| **新增提示词** | 在现有分类下添加新模板 | ⭐⭐ |
| **新增分类** | 创建新的场景分类 | ⭐⭐⭐ |
| **新增技术** | 在核心技术手册添加新技术 | ⭐⭐⭐⭐ |
| **新增文件** | 创建全新的场景文件 | ⭐⭐⭐⭐⭐ |

### 4.2 提交 PR 的步骤

1. **Fork 项目
2. **创建分支**：`git checkout -b feature/你的修改描述`
3. **修改文件**：遵循现有格式
4. **检查质量**：参照下方检查清单
5. **提交**：`git commit -m "feat: 简短描述修改内容"`
6. **推送**：`git push origin feature/你的修改描述`
7. **创建 PR**：在 GitHub 上发起 Pull Request

### 4.3 新增提示词模板检查清单

```
☐ 是否包含 Role / Task / Constraints / Output Format？
☐ 变量是否用 {变量名} 标记？
☐ 是否说明了适用场景？
☐ 是否有填写示例？
☐ 格式是否与同文件其他模板一致？
☐ 是否在相关文件中添加了交叉引用？
```

### 4.4 修改现有内容注意事项

| 修改类型 | 注意事项 |
|---------|---------|
| 修改技术描述 | 确认与论文原文一致，不要凭记忆修改 |
| 修改效果数据 | 标注数据来源（论文/基准/实践） |
| 修改开源项目链接 | 确认链接有效，更新 Star 数 |
| 修改交叉引用 | 确认被引用文件的相关内容仍然存在 |
| 删除内容 | 确认没有其他文件引用该内容 |

## 五、格式规范

### 5.1 当前格式标准

| 元素 | 格式 | 示例 |
|------|------|------|
| **提示词标识** | `<small style="color:#888">提示词：</small>` | 缩小变灰，放在提示词内容上方 |
| **提示词内容** | `**加粗**` | 正常字号，视觉突出 |
| **说明文字** | `<small style="color:#888">...</small>` | 适用场景、填写说明、导航等，缩小变灰，不抢提示词注意力 |
| **分隔** | `---` | 各提示词区域之间 |
| **变量** | `{变量名}` | 必填变量用花括号，可选参数用 `[可选参数]` |
| **技术示例** | 代码块 | SQL、Python 等仍使用代码块格式 |

### 5.2 提示词模板标准格式

```markdown
<small style="color:#888">提示词：</small>

**你是一位{角色描述}。**

**请{任务描述}。**

**约束：**
- {约束1}
- {约束2}

**输出格式：**
## {格式1}
## {格式2}
```

<small style="color:#888">适用场景：{一句话说明}</small>

<small style="color:#888">填写说明：{变量解释}（如有必要）</small>

### 5.3 交叉引用规范

引用项目内其他文件时使用相对路径（GitHub 兼容）：

```markdown
<!-- 从同目录文件引用（带编号前缀） -->
详见 [系统提示词案例](02-AI编程助手系统提示词案例.md)

<!-- 从不同目录文件引用 -->
详见 [核心技术手册](../01-入门与理论/02-提示词工程核心技术手册.md#三链式思维提示chain-of-thought-cot)

<!-- 从根目录文件引用 -->
详见 [核心技术手册](01-入门与理论/02-提示词工程核心技术手册.md)
```

**注意**：文件名中的编号前缀（如 `01-`、`02-`）表示同目录内的学习顺序，引用时必须包含。

引用外部资源时标注来源：

```markdown
数据来源：Wei et al., 2022, [Chain-of-Thought Prompting](https://arxiv.org/abs/2201.11903)
```

### 5.4 Commit 消息格式

```
<type>: <subject>
```

| 类型 | 说明 |
|------|------|
| feat | 新增内容（新模板、新技术、新文件） |
| fix | 修复错误（错别字、格式、链接） |
| update | 更新内容（更新数据、补充示例） |
| refactor | 重构（调整结构、合并内容） |
| docs | 项目文档修改 |

## 七、常见问题

### Q：我不是AI专家，能贡献吗？

*当然可以！** 最有价值的贡献往往来自使用者：
- 发现模板不够好用 → 提 Issue 描述你的场景
- 有更好的提示词 → 提交 PR 添加你的版本
- 发现过时信息 → 提 PR 更新

### Q：如何判断一个提示词模板质量好不好？

参照 [02-核心技术手册.md](../01-入门与理论/02-提示词工程核心技术手册.md) 附录二"四字段标准结构"和附录四"模板迭代方法论"。核心标准：
1. Role 是否具体（"10年后端工程师" > "你是专家"）
2. Task 是否明确（"审查代码" > "看看代码"）
3. Constraints 是否充分（有无字数/格式/安全约束）
4. Output Format 是否清晰（有无具体格式模板）

### Q：如何保持内容时效性？

1. 关注 [01-开源项目与资源索引.md](../10-开源生态/01-开源项目与资源索引.md) 中的项目更新
2. 每季度检查一次论文引用和 Star 数
3. 随时间变化的技术在文档中标注"⚠️ 可能随时间变化"

### Q：文档中的行号会变怎么办？

项目架构文档中的行号是基于当前版本的快照。文件内容变更后行号可能偏移，建议以章节标题而非行号为准。

### Q：新增领域文件需要包含哪些内容？

1. 文件头部：标题 + `> ...` 适用说明 + 导航栏
2. 每个场景：适用场景说明 → 提示词标识 → 提示词内容（四字段） → 说明文字
3. 场景间用 `---` 分隔
4. 变量统一使用 `{变量名}` 标记
5. 更新 README.md 导航和 docs/ 相关文档的交叉引用
